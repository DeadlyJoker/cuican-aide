# 团长交付物复核候选（未推广）

状态：GUI 对照后撤回默认启用；保留原文供后续实验。只在 CrewON 的
办公室/专家团最终汇总输入中追加，不改变 PIM、成员职责、模型或 Run 拓扑。

## 候选原文

验收最终交付物本身，不能把成员的 PASS 当成事实完整的证明。若给出多个方案，逐个核对原始硬约束、前置依赖及资源或预算；改变约束的方案须说明具体改动，重新验算能否达成并保留剩余条件。未经验证的方向只能标为待评估，不得称为可行解法。对用户仅呈现支持决策的必要依据，不展开内部检查过程。

## 施加位置与对照条件

在 `controlOfficeManagerFinalResponseMessage` 与
`controlExpertManagerFinalResponseMessage` 中，紧接“成员报告是待核验材料”
一段之后、用户格式要求之前添加同一段。业务案例实际测的是专家团路径。
完整刷新后，检查落库的团长输入确实含“未经验证的方向只能标为待评估”。
仅依赖开发热更新的那次仍使用旧运行时，单独记录，不算候选。

同一专家团、成员、gpt-5.5、单 worker、无外部工具操作，预算和排期分别用
完全相同的输入在新会话提交。每次均为 2 个专家 Run + 1 个团长 Run。
每个生效变体每个场景仅 1 次，未达到多案例、多次重复、跨模型认证要求。

## 结论

- 复杂排期：未再把单独增加测试人员列为可行改法；给出了增加 1 名开发
  的可核对方案。仍偏长，且没有统一解决所有抽象备选建议的验算表达。
- 简单预算：金额、预算排除、推荐均正确，但多出重复总结，没有减少调用。
- 无可证实的效率收益。完成时间受排队、模型采样、生成长度等影响，不能
  用单次差异作因果判断；也不能把这一结果推广给未测试模型。
- 默认行为已还原。后续应在任务类型/模型的独立对照中考虑此候选，并用
  真实交付物检查约束保留，不能仅以 PASS 或规则存在判成功。
