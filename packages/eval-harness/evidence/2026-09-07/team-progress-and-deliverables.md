# 团队真实进度与交付物验收：续测记录

本轮仅修改 CrewON。所有真实模型任务通过 Web GUI 输入并提交，不使用 API
发起测试，不改 PIM；离线读取本地 Control SQLite 补充结果、Run 数量和时序。
沿用同一专家团“场景验证 · 方案评审 0907”、gpt-5.5、单 worker；无联网、
外部系统读写或实际发布。前轮记录见 [团队场景评估](team-scenarios.md)。

## 已保留的修复

专家任务原先在团长 Run 开始前不显示用户问题，也没有成员进度。根因是
主问题已经持久化，但界面只在最终汇总 Run 启动时收到会话更新。

- 新增独立 UI 进度投影：准备、问题已接受、成员排队/执行/等待/终态。
  状态来自实际接受记录和 Control SSE，不显示后台专家草稿，不生成假进度。
- 专家完成不等于整体完成；团长接受后交回已有最终回复流式通道。
- 生命周期观察处理重复事件、跨 Run 错配、序列缺口、断线重连和运行时销毁；
  重连期间明确“状态待确认”，协调失败不谎称已经取消后台 Run。
- 普通切页返回后保留问题和成员状态；不重复显示问题，也不把尚无主 Run
  的已落库问题显示为 `control_run_missing`。已恢复的真实答案优先于陈旧进度。
- 仅新增只读观察，不改变模型执行拓扑、PIM 请求、持久化协议或运行授权。

真实 GUI：预算场景提交后约 3.7 秒的首次检查、排期场景约 3.3 秒的首次检查，
都已看到问题、成员执行/排队。这是检查时刻，不是逐帧测出的首屏延迟。
预算运行中切到团队页再返回，问题只出现一次；复杂排期捕获到团长仍在输出
半张表格的中间态，之后完整结束。完成后刷新，历史和专家团执行对象仍正确。
宽窗口及 960×640 窗口检查了排版，DOM 未见横向溢出；按仓库设计参考、
设计回归技能保留主会话布局和低干扰状态样式，并增加组件快照。

**限制未掩盖：团队协调仍在页面运行。普通切页不是整页刷新；运行中强刷、
崩溃后的自动续跑尚未修复，也未声称通过。界面明确提醒完成前不要刷新。**
本轮断线游标续接由自动测试覆盖，未执行真实模型运行中的强制断网试验。
前置专家的工具审批入口、整体取消和持久化恢复仍需后续单独处理。

## 新增离线验收底线

`scenario-deliverable-evaluation.ts` 不接入生产决策、不自动批准工作流，不要求
模型改成特殊标签格式；按照 agent-evaluation 技能将事实、语义与效率分开。

- 通知：检查会议时间/主持人、林娜 9月9日18:00 前提供文案、周航演示、
  待补充链接、上线待验收条件及不应出现的发送/批准声明。
  直接复用真实 W1 初稿与 W1-R2 成稿；旧稿遗漏审批新增期限，不能因最后的
  PASS 判成功；纠正稿满足必要事实检查。
- 负例：改错日期/责任人、否定期限、虚构链接、宣称发送或批准上线等。
- 排期：人工把真实方案转成逐日安排，逐个核对容量、工作量、必做范围、
  测试必须次日开始和截止时间。A 先做第6天可全量，B 先做需要第7天；
  第5天可只交付 A。增加测试人员或仅减少测试量都不能解除 B 的开发依赖。
- 候选给出的“增加 1 名开发，A D1–D3 开发、B D1–D2 开发、D3 测 B、
  D4–D5 测 A”也通过了明确改成 2 名开发后的排期检查；原单开发约束下失败。

检查结果始终带 `humanSemanticReviewRequired: true`。通知是特定案例的保守
文本检查，陌生表达/引用可能需要人工确认，不能排除所有语义矛盾；排期检查
只验证输入的结构化安排，不能替人工保证自然语言中的每一项建议都已录入。
目前它们是回归底线，不是已经上线的通用业务裁判。
