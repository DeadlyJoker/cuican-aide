# 团队 GUI 场景评估（2026-09-07）

本轮先改团队目录视觉，再通过真实 Electron / Web GUI 点击和输入运行。只操作 CrewON；不修改 PIM，不用 API 提交测试任务。以下验收标准在提交任务前确定，判断内容与可执行性，不以固定字数或预先告诉模型结论代替质量评估。

共运行6个场景、1次纠正流程后的复测、1次取消测试。模型均为 gpt-5.5，是真实模型调用，不是模拟回答。案例是贴近日常工作的受控材料，不连接外部业务系统、不实际发送通知或执行上线。Electron 用于办公室测试；用户查看 App 后，其余测试移至独立 Web 开发实例，避免打断用户。

## 额外交互覆盖

- 创建、成员职责、办公室搜索、三个模式切换与进入/返回。
- 流式输出、长文本呈现、完成状态、连续追问。
- 工作流人工确认、拒绝、取消、等待审批时刷新、完成后刷新与重新进入。
- 桌面宽窗口、最小窗口、低高度；不改房间运行布局。

## 实测结果

### O1：会议跟进，基本可用但偏冗长

- Electron GUI 新建办公室“场景验证 · 项目推进 0907”，选择 gpt-5.5 执行/规划/验证三个本地成员，逐一设置实际职责。
- GUI 输入 `@本地验证智能体`，准确保留林娜 9月8日18:00、周航“文案确认后1个工作日”、陈悦截止待定，以及9月11日为暂定上线且需要链接检查通过。
- 没有声称已完成任务或发送通知；区分文案完成与文案确认，问题识别有效。
- 质量不足：一个短行动清单扩成6列表格、5项行动、7个追问；增加“当前证据判断/通过”审计措辞，对简单任务阅读负担偏高。
- 只读 Control 事件核实：Run `01a07b39-bff5-7569-855a-c9dc39d50383`，仅1次模型执行，创建至完成23.086秒，首个模型文本增量12.030秒，617个输出增量。事件计时不是逐帧GUI首屏计时。

### O2：核心排期正确，但备选建议存在逻辑缺陷

- GUI 在同一办公室追问：1名开发/1名测试；A开发3天、测试2天；B开发2天、测试1天；测试次日才能开始；截止第5天。
- 正确指出全量不可按期，先A后B最早第6天，先B后A第7天；给出了可执行逐日安排和A先上/B延期方案，标明无返工及上线操作耗时假设。
- 不能判为完全通过：最终“改变约束”建议列了“增加测试资源、压缩测试范围”。单独增加测试人员或压缩测试量仍不能让第5天下班才开发完成的B在第5天通过测试，建议没有逐个复核可行性。
- 另有较多重复：结论、排期后结论、不可行说明、推荐方案、最终建议反复表达同一信息。
- 运行记录为2个成员Run加1个汇总Run，未增加计划Run；两个成员提交后因桌面单worker实际串行执行。GUI捕获到了团长尚未结束的实时文本，后续只读数据库核对完整终稿（用户正在App查看成员设置，避免打断）。
- 建议先改“备选方案的约束复核”评估用例，再做小范围prompt对照；不要只把所有回复强行缩短，也不要为提速默认跳过独立验证。

### E1：预算选型，内容正确但三次调用偏重

- Web GUI创建“场景验证 · 方案评审 0907”，设置团长、业务分析员、约束核验员及各自职责。
- 输入8坐席、3个月、总预算1200元；甲38元/坐席/月+299元，乙45元/坐席/月+99元；两者已确认功能相同，不接受未书面确认的优惠。
- 正确计算甲1211元（超11元），乙1179元（余21元）；推荐乙且没有虚构功能或折扣。
- 两名后台专家加团长汇总共3次Run。结果拆成多节、表格和重复总结，对简单算术选型成本偏高。
- 交互缺陷：专家阶段输入框禁用，但用户消息和进度没有及时出现；直到团长Run启动才开始呈现。这不是“PIM不支持SSE”，而是CrewON尚未把团队前置阶段投影到会话。该项本轮未修。

### E2：发布评审，主要证据判断有效

- 同一专家团GUI连续追问：旧10000请求/100失败，新800请求/12失败；报告宣称稳定性提升88%；门槛失败率≤1%、P95≤800ms，新P95为780ms；灰度仅10分钟；看板无重复但人工抽样发现双重分派；回滚未经演练。
- 正确计算旧1%、新1.5%，指出绝对失败数不能替代比率；P95达标不能抵消失败率不达标。
- 正确保留矛盾证据，要求日志链路、指标口径和回滚演练，不把“未复现”当作排除问题；责任角色和交付证据清楚，没有声称已经执行。
- 未充分解释仅10分钟观察窗口的代表性问题；大量重复信息仍影响阅读效率。
- 执行中切到团队页，后台完成。修复下述恢复问题后，两个场景的原始回答都能通过GUI刷新恢复。

### W1：原流程失败，PASS不等于用户获得交付物

- GUI配置“整理材料与草稿 → 人工确认 → 核验最终交付”。输入9月10日14:00–14:30线上验收会，链接待补充，林娜提供文案、周航演示、9月11日上线需验收后判断。
- 初稿保留已知事实，等待人工确认期间刷新后仍能找回审批，核验节点未启动。
- 审批意见补充“林娜9月9日18:00前提供文案；最终只输出通知正文；不能实际发送”。
- 原流程最后只给 `VERDICT: PASS`，未形成包含新增期限的最终通知，UI也把上游草稿隐藏了，不能判作任务完成。
- 根因有两层：验证节点受严格verdict合同约束，不承担成稿；页面仅显示最后输出。验证节点还给出了过于宽松的PASS，因此仅补UI不能自动证明原流程质量合格。
- 本轮增加“节点产出”折叠区保留真实草稿，验收结论仍独立展示；创建流程时明确提示验证不负责改稿。没有改变运行协议或把草稿伪装成已批准交付。

### W2：冲突材料和人工驳回

- 输入切流材料：10项关键QA有2项失败（含重复分派）、新版本监控未接入、回滚没演练，但变更单宣称全部具备。
- 整理节点识别三项硬缺口并形成阻断建议，未把变更单当可信结论。
- GUI驳回后，人工节点显示已驳回、整体失败、核验节点未开始；只发生1次模型调用。
- 另起测试通过GUI取消：当前节点取消，下游保持未开始，输入框可再次使用。
- 发现一个未修的小窗口状态问题：新任务提交后，轮询取回新执行前会短暂保留上一次执行的状态/结果，不应误认为新任务已通过。

### W1-R2：明确增加成稿节点后交付成功

- GUI创建“提取会议安排 → 人工确认与补充 → 按审批意见成稿 → 独立核验通知”，使用同一输入和审批补充。
- 实际通知正文包含“林娜：请于9月9日18:00前提供文案”，会议时间/待补充链接/上线待验收等约束保留，无实际发送行为。
- 最后独立核验返回PASS；页面默认展开最近的Agent产出，可直接读取通知，较早材料折叠保留。
- 完成后刷新、重进协作流，通知与节点状态仍在。未把这次完成后刷新记为“运行中断网重连测试”。

## 实测后修复的恢复缺陷

### 内部执行会话被启动逻辑选中

刷新时误选最新的隐藏workflow线程，普通聊天展示继承的旧用户消息与工作流内部提示词；没有对应本线程Run的继承记录被错误呈现为 `control_run_missing`。

只读检查确认：原专家团会话仍完整独立；工作流通过fork继承来源历史，并非跨租户串写。侧栏已隐藏这些线程，但启动列表没有相同过滤，导致选择与展示规则不一致。

- 修复CrewON的普通会话列表：过滤工作流/专家定义和fork分支，不影响内部Runtime自己的原始Control列表或按ID读取。
- 新测试覆盖分页、归档、搜索、仅含隐藏线程的空列表。
- GUI刷新两次，专家团两轮回答恢复，无内部workflow消息，无虚假缺失Run错误。

### 专家团执行对象被提前重置

普通Agent目录ready时，专家团目录仍在异步加载；原校验误判专家团不存在，静默改为CrewON。

- 改为按执行对象使用对应目录的加载状态；专家目录loading/unavailable时不据此认定已删除，ready后仍检查是否真实存在。
- 新测试覆盖异步加载、暂不可用、恢复和确实删除。
- GUI重新选择专家团后刷新：历史恢复，执行主体仍是“场景验证 · 方案评审 0907”，没有退回CrewON。

## 下一步建议（没有未经对照就全局改提示词）

1. **优先补团队前置阶段的真实进度。** 在专家分支被接受时显示用户问题与运行/排队状态，团长增量继续走已有流式通道。不能用虚假打字或仅改PIM参数掩盖空白等待。
2. **让验证检查交付物，而不只输出PASS。** 为会议类任务增加确定性事实断言（审批新增时间、待定链接、未授权发送），为排期类任务复核每个备选方案的资源和前置约束。W1原流程仍是失败样例。
3. **简单任务先给直接执行入口，复杂任务保留独立核验。** O1只需1次调用；E1的3次调用没有体现相称收益；O2/E2的独立核对则有价值。提供明确模式选择和按难度的对照评估，不默认所有任务拉满团队，也不盲目取消验证。
4. **区分轮次、排队与内容冗长。** 当前环境单worker导致两个专家串行；增加容量前先评估模型服务限制和CPU/内存。减少重复总结可以先局部改角色输出合同，不采用所有模型统一字数上限。
5. **模型适配以回归证据为依据。** 本轮只验证gpt-5.5，不能推断其他模型表现；后续对每个实际可用模型用同一事实约束案例，分别记录成功、遗漏、错误建议、调用数、排队与完成时间。不要修改PIM端定义。
6. **控制工作流继承上下文。** 目前fork来源会话会带入无关旧任务；这次误选内部线程还放大了继承链。后续应明确展示/选择输入来源，避免把全部旧历史当必要上下文，不直接重写已存历史。

## 覆盖边界

- 已验证本轮团队目录与核心沟通/审批/交付路径；不能称为产品所有能力都通过。
- 尚未覆盖模型执行中强制断网/崩溃恢复、并发用户、工具审批、外部文件/知识库/MCP读写、云端模型切换与跨模型对照。它们需要单独的安全场景和验收，不用本轮纯材料分析代替。
- 一次刷新出现账号服务暂不可用，GUI重新登录后恢复；未修改账号服务，未把单次现象归因于团队代码。
- 真实创建的场景办公室、专家团和两条协作流保留用于复看，没有删除用户历史或修改PIM。桌面App保持运行；独立Web场景库与桌面库不同。
