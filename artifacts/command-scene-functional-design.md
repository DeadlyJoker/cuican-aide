# CrewON 首页三场景与执行主体功能设计

> 本文定义产品方向和功能边界。可直接拆开发任务的请求映射、Agent 指令、持久化、降级、测试与分阶段实施要求见 [command-scene-implementation-spec.md](./command-scene-implementation-spec.md)。两者冲突时，以实施规格为准。

## 1. 问题定义

当前首页的「日常办公 / 代码开发 / 设计创意」只切换标签、快捷任务和输入提示。三者共用同一套模型、权限、上下文资源和结果形态；同时「设计创意」在运行层仍映射到 `code` 模式，因此用户无法理解切换场景带来的实际价值。

本方案将场景定义为一套任务契约，而不是提示词分类：

> 场景 = 场景指令 + 输入与上下文结构 + 能力推荐与解析 + 场景×任务方式 + 交付物 + 权限边界

主会话始终由一个主 Agent 持有。首页默认执行主体是 CrewON，使用 `single` 执行策略；用户也可以选择已定义的单 Agent 或小队。场景只改变工作预设，不创建 Agent，也不自动切换执行主体。用户仍可在场景内增删 Skill、MCP、Plugin 和知识库。

选择单 Agent 时，运行时不暴露多 Agent 工具；选择小队时，主 Agent 使用有界 Team Runtime 拆解、委派和收敛结果。Team 是主会话内部的可选执行方式，不是第四个业务场景，也不是首页的默认状态。创建、编辑和管理 Agent/小队仍在资源库页面完成，首页只选择已经存在且真实可用的执行主体。

## 2. 场景命名与定位

首页使用以下命名：

| 场景 | 一句话定位 | 核心对象 | 完成标准 |
| --- | --- | --- | --- |
| 日常办公 | 把信息和协作事项变成可直接使用的办公成果 | 人、时间、文档、消息、项目事项 | 整理/撰写/分析产出可用成果；协同动作区分草稿、待确认和已执行 |
| 生码 | 从需求或问题出发，完成代码理解、计划、实现或审阅 | 仓库、分支、Issue、代码、测试、PR | 询问有证据、计划可执行、实现有 diff 与验证、审阅有可定位发现 |
| 设计创意 | 从 brief 和参考出发，完成探索、收敛、制作或走查 | Brief、品牌、参考图、页面、组件、视觉资产 | 探索有差异方向、制作可预览、走查有可定位问题、交付规格完整 |

建议将当前「代码开发」改为「生码」。它不只做代码问答，还覆盖计划、实现、验证和审阅；具体完成标准由 mode 决定。

场景按“主要工作对象 + 验证域 + mode 交付物”判定：

- 围绕业务信息、人、时间、文档、消息或知识库，并由事实完整性和协作结果验证：日常办公。
- 围绕仓库、代码、Issue/PR、测试或日志，并由代码证据验证：生码。ask/plan/review 可以分别只产出回答、计划或审阅发现；只有 implement 必须形成 diff。
- 围绕 Brief、Figma、视觉资产、设计系统或界面体验，并由设计标准验证：设计创意。explore/inspect 可以只产出方向或走查发现，不要求正式资产。

跨场景能力不受限制。例如“按 Figma 实现页面”若最终以仓库 diff 和测试验收，属于生码；“走查页面并给设计问题”即使读取前端代码，仍属于设计创意。执行中若主要工作对象或验证域改变，建议在新场景中继续，不静默改写当前任务。

## 3. 三场景功能矩阵

### 3.1 日常办公

典型任务：会议准备与纪要、周报和汇报、项目同步、文档整理、信息检索、任务跟进、知识沉淀。

默认输入：

- 目标：要整理、撰写、分析或协调什么。
- 对象：项目、会议、文档、联系人或时间范围。
- 输出格式：文档、表格、清单、邮件草稿、日程或知识库条目。
- 时限与受众：什么时候使用、给谁看。

默认资源：

- Agent 行为：以办公助理方式工作，优先保证信息准确、结构清晰和行动项可跟进。
- Skill：文档整理、会议纪要、表格分析、信息总结、知识库沉淀。
- MCP：Calendar、Email/IM、Drive/Docs、Browser、Knowledge Base。
- 上下文优先级：最近文档、日程、相关会话、团队知识库、项目状态。

默认执行流：

1. 收集信息并识别缺口。
2. 生成结构化草稿。
3. 校验日期、人员、来源和行动项。
4. 用户确认外部动作。
5. 写入文档、日程、消息或知识库。

关键 Gate：发送消息、邀请他人、修改日程、覆盖共享文档前必须确认。

结果工作台：文档预览为主，侧栏展示来源、行动项、负责人和截止时间；支持复制、导出和外部动作草稿。只有 `coordinate` mode 可进入创建日程/发送的确认流程，其他 mode 的外部按钮保持草稿或提示切换方式。

### 3.2 生码

典型任务：实现功能、修复 Bug、重构、Code Review、补测试、排查构建或 CI、准备 PR。

默认输入：

- 目标：需要实现、修复或验证的行为。
- 工作区：仓库、分支、相关目录或文件。
- 约束：兼容性、技术栈、仓库规范、禁止修改项。
- 验收：测试命令、预期行为、性能或安全要求。

默认资源：

- Agent 行为：以编码代理方式工作，在同一任务内依次完成理解、修改、测试和自审。
- Skill：仓库规范、Code Review、测试生成、依赖分析、远程测试。
- MCP/工具：Filesystem、Terminal、Git、GitHub、Browser、日志与 CI。
- 上下文优先级：AGENTS.md、仓库状态、相关代码、测试、Issue/PR、最近失败日志。

默认执行流：

1. 扫描仓库约束和现有实现。
2. 给出改动计划与影响面。
3. 编辑代码并展示进行中的文件变化。
4. 运行格式化、测试和静态检查。
5. 汇总 diff、验证结果、风险与后续动作。

该流程按 mode 截断：询问只解释和举证，计划只产出实施计划，审阅只给发现，只有「生码/实现」允许修改并进入验证。

关键 Gate：依赖升级、大范围重构、删除数据、完整权限、提交、推送和创建 PR 前按权限策略确认。

结果工作台：Diff 与文件树为主，侧栏展示终端、测试、诊断和 Git 状态。只有 `implement` 可修改、提交、推送或创建 PR；ask/plan/review 的“修复”先显式切换到 implement，再重新经过 Runtime policy。

### 3.3 设计创意

典型任务：创意发散、品牌与视觉探索、页面/组件设计、设计微文案、图像生成、设计走查、交付规范。独立长文、汇报和营销文章默认属于日常办公，避免两个场景重叠。

默认输入：

- Brief：要解决的问题、目标用户和使用场景。
- 品牌约束：风格、色彩、字体、语气与禁用项。
- 参考：图片、网页、Figma、现有产品页面或竞品。
- 交付规格：画布尺寸、平台、格式、数量和截止时间。

默认资源：

- Agent 行为：以设计创作代理方式工作，在同一任务内完成 Brief 解析、方向探索、方案深化和交付检查。
- Skill：设计方向生成、页面走查、图像生成、Figma 设计、设计交付检查。
- MCP/工具：Figma、Image Generation、Screenshot、Browser、Filesystem、素材库。
- 上下文优先级：品牌库、设计系统、当前 Figma 节点、参考图、现有页面、用户反馈。

默认执行流：

1. 解析 Brief、受众和约束。
2. 生成 2–3 个有明显差异的方向。
3. 用户选择方向或混合反馈。
4. 深化页面、组件、文案或视觉资产。
5. 做一致性、响应式和可访问性走查。
6. 输出设计文件、资产与交付说明。

该流程按 mode 截断：探索完成方向对比，走查只输出问题与建议；只有收敛/制作允许修改或生成正式设计产物。

方向选择是协作决策点，不是安全 Gate。关键 Gate 是覆盖现有设计、写入共享 Figma、批量生成付费资产或发布最终资产。

结果工作台：画布/画廊预览为主，侧栏展示方向说明、设计变量、图层/组件、批注和版本。inspect 只展示走查与“进入修复”，explore 只展示方向对比与“选择并深化”；refine/produce 才可进入写入 Figma、导出或正式交付流程。

## 4. 首页交互设计

### 4.1 统一骨架与批准偏离

三个场景共用可见的工作区胶囊、中性 CrewON Hero、场景标签、快捷任务、统一 Composer、上下文入口和能力面板，避免复制三套首页。当前设计 CSS 实际隐藏了工作区胶囊，更新基线时应恢复显示或明确用新的工作区入口替代，不能在规范中“保留”、在实现中 `display:none`。

主 Hero 统一为「让 CrewON 完成你的工作」，场景副标题再表达办公、生码或设计差异。Composer 提供独立的「执行主体」选择器，默认值为「CrewON · 单 Agent」，并可选择已定义的单 Agent 或小队；发送动作统一为「开始任务」。移除以小队为默认的 Hero 和「Agent 小队草稿」文案。这与当前桌面设计产物中的小队首页存在明确冲突，因此 UI 实现前必须更新桌面设计基线和对应设计 Skill。

Scene 与执行主体正交：切换 Scene 不重置用户选择的执行主体，选择 Agent/小队也不改变 Scene、mode、交付物或权限。不可用、未授权或尚未完成运行时支持的执行主体可以显示，但必须禁用并说明原因，不能以假选项进入发送链路。

### 4.2 切换场景时必须发生的变化

切换后同步更新：

1. Scene 副标题和输入框 placeholder。
2. 主任务方式与结构化引导。
3. 快捷任务及其完整 preset。
4. 上下文槽位和 required 状态。
5. 能力推荐、选择来源和真实可用状态。
6. 默认交付物及结果入口。
7. 外部动作说明和关键 Gate。

场景标签下方增加轻量配置条：`任务方式 · 核心上下文 · 默认交付物`。配置条可展开编辑，低高度或窄屏时折叠为一行摘要，不挤压主输入区。

### 4.3 Composer 差异

统一保留模型与本地权限，任务方式默认为「自动」，也允许用户手动覆盖：

| 场景 | 主控制项 | 可选值 |
| --- | --- | --- |
| 日常办公 | 工作方式 | 自动 / 整理 / 撰写 / 分析 / 协同 |
| 生码 | 执行方式 | 自动 / 询问 / 计划 / 生码 / 审阅 |
| 设计创意 | 创作阶段 | 自动 / 探索 / 收敛 / 制作 / 走查 |

用户已选择的模型和本地权限不会随 Scene 切换。权限文案使用「自动执行本地操作 / 需要时请求批准」，不承诺每次本地操作都弹窗；“完全访问”不作为 Scene 默认，也不放在一级 Composer 控件，若保留则进入带明确警告的高级设置。外部动作始终由独立 Gate 管理，`confirm-each` 不接受自动批准或历史记忆批准，避免把“自动本地执行”误解为“自动发送或发布”。

输入框上方允许添加稳定引用的场景上下文：

- 日常办公：文档、会议、联系人、日期范围。
- 生码：仓库、分支、Issue/PR、文件、日志。
- 设计创意：Brief、图片、Figma 节点、品牌库、画布规格。

### 4.4 快捷任务与选择来源

每个场景展示四个高频任务：

- 日常办公：`整理今日工作`、`生成会议材料`、`撰写项目汇报`、`沉淀知识库`。
- 生码：`实现一个功能`、`修复一个 Bug`、`审阅当前改动`、`补齐测试与 CI`。
- 设计创意：`探索设计方向`、`设计页面或组件`、`生成视觉资产`、`走查并交付`。

快捷任务同时设置任务方式、交付物、推荐能力和上下文槽位。每项选择记录来源：场景默认、快捷任务或用户。切换 Scene 只替换场景默认；用户选择必须保留，快捷任务项只标记不匹配，不静默删除。

### 4.5 响应式要求

- 低高度窗口使用正常文档流和纵向滚动，不把 Hero 绝对定位在视口中央。
- 风险条、输入框和发送按钮始终可见且不重叠。
- 宽屏结果区可双栏；窄屏将「会话 / 结果」作为一级 Tab。
- Scene tabs、配置 chip 和能力 chip 不产生横向溢出。

## 5. 任务创建、运行态与完成态

### 5.1 条件式预检

不为每个任务强制弹出任务卡：

- 低风险且上下文足够：直接开始。
- 非阻塞信息缺失：Agent 使用明确假设继续。
- required context 或 required capability 缺失：在 Composer 内联阻止并给出修复动作。
- 预计有外部写入或高风险动作：显示紧凑风险条；真正执行时再由 Runtime Gate 强制确认。

### 5.2 真实运行态

「收集→草拟→校验」「理解→修改→测试」「Brief→探索→交付」是场景心智模型，不是固定进度条。UI 只展示真实可观测事件：模型计划、Tool/MCP 调用、文件变化、验证结果、产物和审批。没有结构化事件时使用通用状态，不伪造阶段、百分比或完成情况。

运行态由服务端解析后的执行主体决定。CrewON 默认主体和已定义的单 Agent 使用 `single`，移除多 Agent 工具；已定义小队使用 `team`，只开放有界的委派、状态与收敛能力。Agent 可以暂停请求确认；只有已选择且运行时确认可用的小队才显示成员状态。

### 5.3 完成态

统一保留 transcript，先将真实文件、diff、测试、图片、Figma 节点和外部草稿投影为多产物清单，再选择首要结果视图：

- 日常办公：Document Adapter。
- 生码：Code Adapter。
- 设计创意：Design Adapter。
- 没有实体产物：Conversation fallback，并说明本次只生成文本结果。

完成态必须处理部分失败、资源失效、验证过期和重试，不只支持“成功/无结果”。

结果区按钮不是后门：每个动作都按当前 Scene × mode × policy 计算为本地可用、仅草稿、需切换 mode、需确认或禁用，并通过正常 turn/Resolver/Gate 链路执行。

### 5.4 场景切换规则

- 空白任务：立即切换 ScenePreset。
- 已输入未发送：保留正文、附件和用户选择，重新计算场景默认并标记不兼容项。
- 已运行任务：Scene 固定。
- 需要改变主要交付物：使用「在新场景中继续」，新任务只引用原任务的有界摘要或产物。

执行主体采用相同的线程身份边界：空白任务和未发送草稿可自由切换 CrewON/Agent/Team；线程创建后执行主体固定。需要从单 Agent 改为小队或更换 Agent 时，使用「由其他执行主体继续」创建新任务，只传递有界摘要和产物引用，避免在同一历史中途替换可信指令、权限和成员定义。

## 6. 产品与 Runtime 数据边界

前端新增独立 `SceneProfile`，不要再用只有 `office | code` 的 `WorkMode` 表达首页场景。产品概念分为：

- `ScenePreset`：展示、推荐和上下文槽位。
- `SceneTaskContract`：Scene × mode 的交付物、本地写入与外部动作边界。
- `ResolvedCapability`：区分推荐、选择、可用和实际激活。
- `ExecutionTarget`：CrewON 默认主体、已定义单 Agent或已定义小队；服务端解析为 `single` 或 `team`。
- `ArtifactManifest`：从真实事件得到的多产物清单。

默认 `executionStrategy` 为 `single`。服务端根据执行主体解析最终策略：CrewON 和单 Agent 为 `single`，小队为 `team`；客户端不能直接提交或伪造策略。`single` 必须由 Runtime 移除多 Agent 工具，不能只依靠提示词；`team` 只在对应小队真实存在、已授权且 Team Runtime 可用时启用。Scene 与执行主体元数据必须在 app-server v2 持久化并覆盖恢复、压缩和 fork。旧任务显示为「通用/历史任务」，不静默映射成 code。

已标记 Scene 的任务若找不到保存的 Registry 版本，必须 fail-closed 为只读和仅草稿，清空可执行能力，并引导用户在当前版本新建同场景任务；不能用最新版指令猜测恢复。

版本号、`executionStrategy`、contract revision 和有效写入策略都由服务端决定。每次 contract 变化写入可回放事件；rollback 和 fork-at-turn 从对应历史点恢复，不能直接取源线程当前“最新配置”。

`ask / plan / review / inspect` 的只读边界必须由 Runtime 将 Scene policy、用户权限和宿主限制取最小值后强制，用户选择“完全访问”也不能把只读任务变成可写任务。

场景指令由服务端可信 Registry 生成。客户端不传任意 developer instructions，也不把文件名、用户 Brief、Plugin/MCP 描述等不可信字符串提升到 developer 权限上下文。详细字段和限制以实施规格为准。

Scene Registry 是 mode requirements、context slots、capability tags、版本和完成检查的唯一真源；前端通过 `scene/list` descriptor 渲染，不维护另一份运行时默认值。客户端版本只做兼容检查，不能选择或降级服务端版本。

首发通过 `sceneRuntime` experimental API 与前端 feature flag 灰度；完成恢复兼容和指标验证后再评审稳定化。

## 7. 参考 Codex 的能力分层

Codex 的区分不是一个“办公/编码/设计”开关，而是多层组合：

| 层级 | 职责 | CrewON 用法 |
| --- | --- | --- |
| Collaboration Mode | 计划或默认执行等横向交互方式 | 与业务 Scene 正交；`code.plan` 可映射 Plan，其余默认 Default |
| Trusted Instructions | 稳定角色、完成标准和边界 | 服务端按 Scene/version 生成，不由浏览器拼接 |
| AGENTS.md / 空间规则 | 仓库、品牌或空间级持久约束 | 生码优先加载仓库规则；办公/设计可加载组织或品牌规则 |
| Tool | 可执行的原子能力 | Resolver 根据真实 tool inventory 判断 exposed，不把推荐当启用 |
| MCP / App | 外部数据和动作 | 用结构化 mention 和连接状态激活日历、GitHub、Figma 等能力 |
| Skill | 具体任务的专业工作流 | 转换为真实 Skill input；适合纪要、Review、设计走查，不代表整个 Scene |
| Plugin | Skills、MCP、App 和元数据的分发包 | 只负责安装、发现和来源；模型不能直接“调用 Plugin” |
| Approval / Tool annotations | 动作风险、审批和审计 | 复用 read-only、destructive、open-world 等标注，缺失时保守处理 |
| User Context | 当前目标、附件与资源引用 | 保持用户或不可信权限，不承担全部场景差异 |

因此 CrewON 的关系是：

```text
Scene Profile
  ├─ 场景身份、mode 与交付物
  ├─ 可信场景指令
  ├─ 能力推荐
  ├─ Runtime Resolver → Skill / MCP / App / Tool
  ├─ 本地写入策略 + 外部动作 Gate
  └─ Artifact Projection → 结果 Adapter
```

场景是编排层，Skill 是方法层，Tool/MCP/App 是执行层，Plugin 是分发层。三个场景不能各做成一个不可拆分的大 Plugin，也不能依赖某个 Plugin 才能进入；缺失能力时应展示安装或诚实降级。

当前实现中 Scene 仍主要是表现层状态，design 还映射到 code。目标不是简单扩展 Collaboration Mode，而是新增 Scene Runtime，并让选择真正转换成模型可见的可信合同和结构化能力输入。

## 8. MVP 范围

MVP 必须同时包含产品可见差异和最小 Runtime 闭环：

1. 「代码开发」更名为「生码」，三个 Scene 有不同副标题、Composer、快捷任务、上下文和结果入口。
2. 快捷任务应用完整 preset，选择来源可见且可恢复。
3. Runtime 校验 Scene × mode，并注入服务端可信合同。
4. Skill/MCP/App 选择转换为真实结构化输入，能力状态不造假。
5. app-server v2 持久化 Scene/version，恢复、压缩和 fork 一致。
6. 默认 CrewON 和单 Agent 目标关闭 multi-agent runtime；选择可用小队时启用有界 Team Runtime。
7. 外部动作在强制 Gate 完成前一律只生成草稿。
8. 运行态只展示真实事件，完成态基于 ArtifactManifest。
9. 桌面端、低高度和窄屏有快照覆盖。

MVP 不做：

- 三套独立首页。
- 屏蔽跨场景能力。
- 新的设计后端执行模式。
- 任何真实 external write：发送、推送、写入 Figma、发布或付费操作在首发 MVP 中都只生成草稿，即使用户确认也不执行。完成 B2 后可作为 v1.1 feature flag 逐次确认开放，但永不支持无需确认的自动外部执行。
- 在首页创建、编辑或管理 Agent/小队；首页只选择资源库中已有的执行主体。
- 由 Scene 自动切换 Single/Team，或让客户端直接控制 `executionStrategy`。

## 9. 验收标准

- 不看 Scene 标签，仅看 Composer、上下文、能力和结果入口也能识别场景。
- 相同用户输入在三个 Scene 下产生不同的合法 Runtime Contract，而不只是不同 prompt。
- 推荐、已选择、可用、实际激活四种状态不混淆。
- `ask / plan / review / inspect` 不产生工作区修改；可写 mode 仍遵守本地权限。
- CrewON 默认主体与单 Agent 的工具清单中不存在多 Agent 工具；小队仅包含受限 Team 工具。
- Scene 切换不改变执行主体，执行主体切换不改变 Scene 契约。
- 切换 Scene 不丢失草稿、附件、模型、权限或用户选择。
- 外部高影响动作没有 Runtime Gate 时只能生成草稿。
- Scene、版本、能力、上下文引用和结果产物可恢复、审计。
- 旧任务不被错误注入 code Scene。
- 桌面、低高度和窄屏不遮挡、不横向溢出。

## 10. 实现顺序

1. D0：先更新默认单 Agent、可选 Agent/小队的桌面设计产物和 `crewon-design-reference`，设为唯一验收基线。
2. A0：建立 Scene UI Domain。
3. A1：可信 Runtime Contract、Execution Target Resolver、fail-closed guard、真实能力输入和按主体解析的 tool policy。
4. A2：app-server v2 持久化及完整线程生命周期。
5. B1：Capability Resolver 与缺失能力降级。
6. C0：Artifact Projection。
7. C1–C3：Document、Code、Design Result Adapter，首发外部动作保持 draft-only。
8. B2（v1.1）：跨工具通道的外部动作和破坏性动作 Runtime Gate，经验证后逐次确认开放。

每阶段都要有对应行为测试；详细拆分、字段和命令见实施规格。

## 11. Agent Team 与本地多 Agent 边界

首页现在支持选择已定义的小队，但本节中的本地多 Agent 调度、工作树隔离和高级编排仍可分阶段落地。若 Team Runtime 尚未在某个部署中可用，对应小队必须显示为不可用并阻止发送。

### 11.1 主会话模型保持不变

无论 `single` 还是未来的 `team`：

- 用户只和主 Agent 对话。
- 主 Agent 持有完整任务目标、用户约束和最终回复权。
- 子 Agent 不直接改写主会话历史。
- 子 Agent 的输出以有界结果、产物引用和状态事件返回主 Agent。
- 权限申请、人工 Gate、取消和失败恢复都由主会话统一呈现。

切换为 Team 时，界面可以在运行详情里展示「主 Agent 正在调用 3 个专业 Agent」，但主 Composer、主 transcript 和场景标签不改变。

### 11.2 当前应预留的数据边界

为了以后不重构历史和事件模型，当前可以保留以下概念，但默认只有一个参与者：

```ts
type AgentParticipant = {
  agentId: string;
  role: "primary" | "worker" | "reviewer";
  status: "idle" | "running" | "completed" | "failed";
};

type TaskEvent = {
  eventId: string;
  taskId: string;
  sourceAgentId: string;
  type: string;
  createdAt: number;
};
```

单 Agent 执行目标：

- `executionStrategy = "single"`。
- `participants` 只有一个 `primary`。
- 所有事件的 `sourceAgentId` 都是主 Agent。

小队执行目标增加 worker/reviewer，不修改已有单 Agent 记录的含义。

### 11.3 本地多 Agent 的后续方向

本地多 Agent 可以采用「主 Agent 调度器 + 有界 Worker」模型：

1. 主 Agent 将任务拆成带输入、输出格式和权限边界的子任务。
2. 本地调度器限制并发数量、运行时间和上下文大小。
3. Worker 使用独立上下文，不复制整段主会话历史。
4. Worker 按任务获得最小化的 Skill、Tool、MCP 和文件范围。
5. Worker 返回结构化结果、产物路径、验证记录和未解决问题。
6. 主 Agent 负责冲突处理、结果合并、最终验证和用户沟通。

生码场景还需要额外处理：

- 默认避免多个 Agent 同时修改同一工作树。
- 可按 Worker 创建独立 worktree 或文件所有权范围。
- 合并前由主 Agent 检查 diff、测试状态和冲突。
- Git 提交、推送和创建 PR 仍由主 Agent 统一发起并经过 Gate。

办公和设计场景则更适合按产物拆分，例如一个 Worker 做资料收集、一个做草稿、一个做审阅，但最终文档或设计版本仍由主 Agent 收敛。

### 11.4 上下文与稳定性要求

未来多 Agent 必须保持：

- 主会话历史增量追加，不由子 Agent 重写。
- 给每个 Worker 的上下文有硬上限。
- 单个返回项有大小上限，长内容通过文件或产物引用传递。
- 主 Agent 只接收完成当前决策所需的摘要和证据。
- 子任务、工具调用、文件变更和审批都有可恢复的事件记录。
- 主 Agent 被取消时，能够级联取消仍在运行的 Worker。

首页选择器必须先使用统一的执行主体模型；具体 Team Runtime 可以按部署能力逐步开放，但不能用 Scene、提示词或前端布尔值伪造小队已启用。
