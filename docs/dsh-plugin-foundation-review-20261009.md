## 研究依据

DSH 官方仓库明确引用 Cordis 的论文 **A Programming Paradigm for Spatiotemporal Composability**。论文作者为 Yifan Shi、Wei Zhang、Tianyi Cui，arXiv:2608.25512v1，2026-08-26，92 页；它研究动态组合的机制与边界，并非短剧产品或性能优化论文。[论文与版本](https://arxiv.org/abs/2608.25512v1)、[全文](https://arxiv.org/pdf/2608.25512v1)。

源码核对基于 DSH 提交 `d743267388641bc76f17c45ce8b4c231aed1d32c`。实际检查 `packages/core/tools/src/index.ts` 中的工具注册、范围限制和 disposer，以及官方架构、服务依赖和开发文档。DSH 正处开发者预览，不能把当前接口当作 CrewON 长期稳定 ABI。[官方仓库](https://github.com/deepseek-ai/deepseek-harness)、[固定提交的工具实现](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/packages/core/tools/src/index.ts)。

## 精髓与适用边界

论文 §3、§5 将可撤销的运行时修改与可响应变化的依赖组合到 Context；§5.1 的恢复按后进先出组织。§6 则限制其保证：外部已发生的写入不能凭卸载逆转；清理函数是否正确仍由作者承担；语言级依赖访问约束不等于恶意代码沙箱；独立构建还需要版本兼容治理。这些限制必须和机制一起采用。[论文 §3、§5–6](https://arxiv.org/pdf/2608.25512v1)。

DSH 用服务接口连接提供者和消费者，必需依赖未就绪时等待，依赖撤下时清理消费者，返回后重新加载；同名服务可按上下文分别组合。[服务依赖](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/docs/user/develop/framework/service.md)。

DSH 的模型、工具、会话、循环和 UI 都可作为插件配置；bundle 是分发单元，profile 是运行组合，Web 和桌面通过共享运行路径装配。扩展能力需要接口定义、实现和消费者三者配套。[架构](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/docs/architecture.md)。

对 CrewON 的工程结论如下。这是结合现有约束提出的设计，不是论文原话：

| 原则                       | CrewON 应落实的行为                                          | 验收方式                                   |
| -------------------------- | ------------------------------------------------------------ | ------------------------------------------ |
| 注册必须有所有者           | 工具、页面、事件、订阅、计时器都归属插件实例；注册和清理相邻 | 卸载后不存在该实例的新入口、监听或后台轮询 |
| 依赖必须可检查             | 服务名、API 版本、作用域、必需/可选声明；缺失原因可定位      | 缺失只阻止对应贡献，恢复不要求重装整个 App |
| 提供与消费通过契约连接     | UI 和 Agent 使用同一用例；不导入插件业务实现                 | 仓外包不引用宿主源码，两个入口产物一致     |
| 生命周期不能靠页面状态推断 | 分开安装、授权、选定版本、激活和服务健康                     | 已启用但依赖故障时显示准确原因，不伪报可用 |
| 组合必须可重建             | 确切包摘要、配置修订与服务绑定可审计；基础装配与业务装配分开 | 冷启动恢复同一选择，Web/桌面公开能力一致   |
| 状态与插件代码分离         | 历史任务和产物由稳定端口读取                                 | 卸载仍能查看基础历史，重新安装不复制原项目 |

不直接把 DSH 的全部运行时替换进 CrewON。先沿用 Node 24、pnpm 10、现有 Run/Tool/SSE 和多租户授权架构，提炼可组合契约。是否直接采用 Cordis，需要后续架构决定与兼容验证。

## 基础能力与扩展范围

| 范围                                                    | 决策                                               |
| ------------------------------------------------------- | -------------------------------------------------- |
| 账号、租户、权限、凭据、任务回执和恢复                  | 宿主权威；业务插件不能替代授权或任填调用身份       |
| 首页聊天、附件、模型目录、模型选择、发送/停止、流式重连 | 基础能力；零业务插件时可用，插件复用相同公开接口   |
| 工作空间、会话绑定、历史与设置                          | 保持原版行为，先建立可重复的回归基线               |
| 模型与工具提供者、Skill、业务工作流                     | 通过服务接口组合；可替换实现不意味着可绕过宿主政策 |
| 业务页面、局部导航、产物编辑器                          | 仅在明确贡献点与实例根节点内改变，使用宿主主题     |
| 整个 UI shell 或 Agent 循环替换                         | 应用装配级别的独立架构范围，普通业务插件无此权限   |

Skill 提供任务方法和指导，不承担服务授权、存储事务或执行幂等。插件注册能力，Agent 按当前会话范围发现和执行能力；两者都复用基础运行路径。

## 配置隔离的实施决定与约束

源码确认 `apps/control-api/src/main.ts` 在分配数据库之前读取 Native bootstrap 和各插件执行授权，`desktop-plugin-configuration.ts` 同时严格校验身份、scope、来源摘要和项目业务配置。当前任一字段错误会阻断 Main 启动。这不是可以用一个 catch 忽略的普通业务表单错误：从损坏文件取出 actor 后启动基础服务，会把未经校验的数据当作身份权威。

隔离必须遵守以下顺序，当前尚未实施协议升级：

1. 从 Native 的可信生命周期获取并独立校验基础服务身份、登录会话、存储路径与权限。插件文件不提供基础身份；基础授权出错仍拒绝启动。
2. 将安装管理的包来源批准与业务服务绑定分成明确的配置单元，各保留拥有权、字节固定、版本和当前性检查；不能从业务文档静默推导管理授权。
3. 在独立验证基础与管理权威后，加载各插件业务服务；一个配置单元失败只撤回该单元及依赖贡献。诊断保留插件、服务和错误码，日志不输出凭据或原配置正文。
4. 基础聊天和设置管理保持可用；未准备成功的插件拒绝执行，界面显示实际原因。已提交的配置与实际激活结果分开展示，不能再把“保存成功”称作“服务可用”。
5. v1–v3 保持原严格解析和摘要语义，不能删除未知字段校验；新装配使用明确的新版本和相邻迁移，覆盖旧包、冷启动、原回执及多账号边界。

必须先有基础独立权威，再实现可恢复的业务加载。配置隔离验收包括损坏来源批准、错误 scope、业务服务版本不兼容、插件缺失与基础会话继续可用；前三者不能通过放宽授权来获得绿色测试。

资源生命周期另一个差异是 Node SDK `onDispose` 只允许 setup 期间注册；它不能直接等同于 DSH 支持运行时新增 effect 的 Context。现已增加可检测的运行期资源获取接口，保留原 setup 注册边界，覆盖异步获取中撤权、借用保留与清理失败，详见[运行期资源协议](./plugin-runtime-resources-protocol.md)。这没有完成依赖自动重协调或历史 Run 获取作用域，F3 仍未完成。

### 已实施第一步：Native 插件准备失败隔离

### 基础启动修复：零插件且未配置模型

原 Supervisor 在模型提供者与 Native 插件批准都不存在时直接返回，不启动 Control。该行为与“基础能力独立于插件”冲突，现改为启动仅有基础管理能力的 Control：不启动 Worker、不执行 release、不探测供应商、不授予插件管理 access。基础设置、会话和存储继续由原 Native 身份、会话令牌及 CSRF 保护；没有新身份或免登录入口，也未改变宿主 UI。

编排测试覆盖此状态的启动、停止和同一 Native owner 重启；同 owner 的会话令牌按既有生命周期保持，真实进程冷启动的旧令牌拒绝行为仍由前述专项覆盖。现有编排、模型选择与故障隔离 41/41 通过，零跳过。

增加实际 Control Main 进程验收：去除插件批准与全部模型环境后，原 SQLite 会话仍可经具名认证客户端读取，错误令牌返回 401，插件目录返回 404，业务历史/积分计数保持。与原卸载冷启动专项共 2/2，通过；Control 和桌面 Host 类型检查通过。此验收仍使用临时数据库，不等于用户正式桌面或真实聊天发送验收。

## 必须覆盖的失败行为

跨插件依赖的实际执行范围、组合锁、相邻 Run 绑定与新授权恢复顺序见[依赖协调设计](./plugin-dependency-reconciliation-design.md)。现有底层升级顺序已通过真实安装 ESM 专项验证，但生产 `PluginExecutionPackage` 仍是每包私有宿主；自动协调不能绕过这一持久边界。

缺失必需服务、可选服务缺失、重复贡献、循环依赖、不兼容版本、启动中撤权、设置保存成功但激活失败、清理失败、旧请求回执未知、升级后旧任务恢复、无插件冷启动、插件目录不可用但普通聊天可用。每种行为都必须给出有用且准确的用户状态。

卸载清理只针对实例的运行时注册与资源；持久业务事实不会逆向消失，付费或外部执行也不会凭卸载撤销。可信同进程 Node/UI 模式继续明确标识；未实现的隔离模式拒绝运行。

## 基础模型发现：凭据失败不复用旧目录

正式 Main 原来把所有非 `ok` 的目录探测结果折叠为 `null`。Supervisor 对 `null` 使用同 endpoint/API Key 的原缓存，明确凭据拒绝或绑定失效也可能启动旧模型 Worker。现 Main 区分失败类型：`credentialMissing`、`authenticationFailed`、`bindingMismatch` 转为已知不可执行的空目录，覆盖该 Key 的旧缓存；Supervisor 沿用原空目录路径，只启动基础 Control。临时网络、限流和供应商响应故障仍保留同 Key 缓存，不跨 endpoint 或 Key 使用。成功探测恢复后按返回目录启动原运行器。没有改 HTTP、探测输出、缓存 schema、模型筛选或 UI 样式。

新增真实子进程编排回归验证同一 Supervisor 从成功目录、凭据拒绝、再次离线重启到成功恢复；拒绝后没有 release/Worker 子进程。目录、凭据解析、Supervisor、可选插件隔离和基础管理相关 48/48 通过，零跳过；桌面 Host 类型、边界和格式检查通过。子进程入口是审计/HTTP 测试夹具，不等于正式 App 或真实外部模型验收。Mac 锁屏已重新检查并请求解锁；正式 App 未替换，用户插件保持卸载，F1 仍未完成。

## 独立开发工具：复用宿主包校验

F4 增量加入私有工作空间包 `@crewon/plugin-tools`，本地 tarball 分发给仓外开发项目；不发布注册表，不更改 SDK ABI、插件包协议或产品运行时。架构决定是沿用 Node 24、pnpm 10 和现有 esbuild，将 `@crewon/plugin-host/package-snapshot` 的权威文件校验器及纯契约闭包打入命令。独立项目不依赖宿主源码、workspace 链接或运行时包，不引入另一套文件校验规则。构建白名单阻止误打包 Application、Store、执行器及插件加载器，外部导入只允许 Node 标准模块。

`crewon-plugin check <package-directory>` 按原默认限制检查描述符和真实产物字节，输出版本化 JSON、原包摘要及声明的服务/贡献点；不安装、不执行入口、不授权、不解析实际服务依赖。校验快照不是签名或持续可信证明，安装器仍须重新捕获并授权。报告协议与退出码见 [工具说明](../packages/plugin-tools/README.md)。

真实 tarball 在仓外离线安装和实际 bin 调用通过。单个分发集成用例覆盖与宿主摘要一致、入口未执行、原文件未改、篡改、缺失、未声明文件、符号/硬链接拒绝、不支持的宿主 API、非法参数和错误信息不暴露绝对路径。工具类型检查通过；该测试不是插件安装/升级/回滚闭环，F4/F5 仍未完成。临时独立项目由 finally 删除。用户业务插件保持卸载，正式 App 未更新。
