# 插件服务依赖协调设计

状态：纯组合锁契约、公开 SDK 与底层行为验证已实现；持久化、跨插件运行层与自动协调尚未实现。后续实施依据此设计，不把自动恢复等同于自动授权。

## 当前代码的实际边界

- `PluginNodeHost` 捕获提供者身份和精确服务版本。撤下提供者时会撤下当前消费者；已有借用保留原消费者及其提供者。升级存在当前消费者时拒绝，避免隐式改绑。
- `PluginExecutionPackage.open` 为一个精确包创建私有 NodeHost。原注释明确要求跨包依赖有单独持久锁，不能从今天的安装选择解析历史 Run。生产执行不是一个全局 NodeHost。
- `PluginNodePreparedActivation` 的 commit 再检查当前性、依赖和宿主授权。重新执行 setup 不构成重新授权，也不保证可发布。
- 目前消费者不会因为提供者回来而自动恢复；已新增公开组合锁的纯解析/摘要接口，尚未保存到 Store，也没有事务化的多插件选择更新。

DSH/Cordis 的可迁移原则是：服务存在性决定生命周期，撤下提供者先撤下消费者，资源按归属收尾，提供者恢复后重协调受影响的消费者。CrewON 还必须保留身份、profile、原 Run 和持久授权边界，不能直接把全局响应式容器引入执行层。

## 装配范围与权威

一个装配实例属于一个明确 tenant、space、profile 和宿主 authority epoch。宿主版本化服务、插件提供者与消费者均在该范围解析，不从另一账号、profile 或另一个运行实例借服务。

安装选择表示期望配置，不表示已激活。协调器读取宿主持久选择和来源批准，核验真实包后计算依赖图；准备、重新准备与发布都重读当前批准和选择修订。Native 或正式服务签发身份，插件文件不能提供或覆盖基础身份。来源批准错误仍撤回插件权威，基础账号、设置、聊天服务继续由独立权威运行。

协调器只管理业务插件组合，不掌控宿主 UI、账号或模型凭据。基础服务不依赖业务插件；发布只开放已有贡献槽。

## 持久组合锁

独立协议 `crewon.plugin-composition-lock.v1` 已通过 `@crewon/contracts/plugins` 和编译 SDK `@crewon/plugin-sdk/contracts` 导出创建、严格解析与激活顺序接口；当前没有数据库表。锁包含：

| 部分     | 必需内容                                                                                                                                        |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 装配身份 | tenantId、spaceId、profileId、authorityEpoch 与组合 revision                                                                                    |
| 精确节点 | pluginId、publisherId、version、packageDigest、hostApi、各选择的 selectionRevision，以及完整 requires/provides 声明；不可使用可变源目录代表身份 |
| 服务边   | 消费者节点、服务名、精确 API 版本、必需/可选、精确提供者节点或具名宿主实现修订                                                                  |
| 可选缺失 | 显式记录 absent；不能恢复时从当前目录偷偷补上提供者                                                                                             |
| 内容身份 | 对标准化字段与稳定节点/边排序计算摘要；排除令牌、密钥、服务对象和函数                                                                           |

宿主服务可按精确版本共存；插件服务遵循当前 NodeHost 的同名贡献冲突规则，不能选择“最后安装的那个”。缺必需服务、版本不匹配、重复贡献或无法解开的环均保持不可用，并给出具体节点和服务原因。循环依赖先通过绑定组件拆开，不先引入会绕过启动约束的代理对象。

规模限制为 64 个插件、每节点 64 条服务声明、1024 个宿主服务、最多 4096 条边，同时受 512 KiB 完整文档、65536 个 JSON 节点及 16 层深度限制；不能保证所有逐项上限组合同时容纳。创建端也校验推导出的边与摘要所占总预算，不能产出自身解析器无法读取的文档。宿主端不向模型注入整张图，只提供当前任务相关的有界能力信息。

## 纯契约的接口与约束

- `createPluginCompositionLock(specification, digester)`：输入 scope、revision、精确节点与宿主服务声明；从声明推导每条服务边，记录可选缺失，拒绝缺必需依赖、贡献冲突、自依赖与循环。
- `parsePluginCompositionLock(value, digester)`：拒绝额外字段、非法 JSON、缺失/重复或改变的边、错误提供者和摘要；不会静默补回依赖。规范化顺序使用稳定代码单元排序，数组声明顺序变化不改变语义摘要。
- `pluginCompositionActivationOrder(value, digester)`：先严格解析和验证摘要，再返回确定的提供者在先的顺序。

摘要覆盖 scope、authority epoch、组合与选择修订、节点身份、完整声明和边。它是内容完整性校验，不是签名或授权；字段中的 scope 也不证明调用者拥有该租户。文件真实性、服务实际就绪、当前批准与历史恢复许可仍必须由宿主核验。解析过程复制冻结数据，不调用 getter/toJSON，未引入文件路径、密钥、服务对象或插件代码。

## 变更与恢复顺序

1. 从当前持久选择核验全部目标包和来源，构建候选图；不执行插件代码。先诊断冲突、缺失和环。
2. 对比原锁与候选图。改变精确包、必需依赖或可选依赖存在性的节点，连同依赖它的消费者进入受影响集合；无关实例不重启。
3. 撤回受影响实例的新准入和贡献，先消费者、后提供者。只取消资源获取；旧借用保留原实现和已取得资源，物理清理按原租用释放进行。
4. 在候选图上按依赖顺序准备提供者和消费者；消费者明确捕获候选提供者身份。每次 setup 后重新读取持久批准，commit 用同步修订栅栏检查当前性。
5. 发布与记录实际激活结果。单元失败时撤销其候选资源及依赖消费者，不把保存成功显示为可用。旧图只在批准仍有效且原选择允许的情况下保留；不能为了“恢复成功”重启已撤权节点。
6. 服务回来时只对仍在期望配置中且重新通过授权的消费者重协调。频繁更新合并到最新修订，但不能合并掉一次撤权；撤权同步阻止新准入。

不能声称整个多节点变更是单事务：文件核验、异步 setup 和外部服务均在存储事务之外。存储只原子记录期望修订/组合摘要，实际发布必须逐项带当前性栅栏；中断后的恢复读取两者差异，不重做未知外部操作。

## 原 Run 与相邻版本兼容

现有 `crewon.extension-run-binding.v0` 的摘要配方和严格字段集合保持。拟新增相邻绑定版本，通过组合锁摘要引用精确图，不能把完整图塞进现有 8 KiB 绑定文档。

新 Run 的准入、选择修订、组合摘要和现有工作项/计费预留同事务持久化。恢复读取该 Run 原组合锁及精确包，重新校验历史恢复权威，不使用今天的 profile 选择。没有原锁的 v0 Run 只走原适配路径，不伪造跨包图。

旧借用的提供者只能在全部依赖租用释放且清理成功后退休。组合锁、包和产物仍有 Run/回执引用时不回收。未知 ComfyUI 操作只查原回执，不能因插件恢复或配置更新重新派发。

## 已验证与实施入口

实际安装 ESM 包的专项已验证：消费者使用提供者 v1；撤回消费者后发布 v2；旧借用仍读 v1；消费者重新准备后 commit 被拒绝时没有重新开放准入；新授权批准消费者后，新借用读 v2，旧借用仍读 v1；旧借用释放后 v1 清理；无关插件没有再次 setup。NodeHost 整组 17/17 通过，零跳过。

纯组合锁专项 12/12 通过，覆盖规范化、精确宿主版本、可选缺失、篡改、冲突、循环及完整输出预算；契约包完整回归 700/700、编译 SDK 完整回归 88/88 通过，包含公开编译入口和原仓外离线声明验证。类型、边界及格式检查通过。

这证明底层机制可支持指定协调顺序及纯组合锁协议可分发，不证明存在自动协调器、Store 持久化、真实 Run 的跨插件锁或生产装配。

实施顺序：纯契约与摘要/图校验 → 原 Store 的组合锁与相邻 Run 绑定事务 → scope 内协调器与撤权/关闭路径 → `PluginExecutionPackage` 的显式原锁依赖装配 → 原 UI 的状态诊断 → 独立最小插件安装/升级/回滚/停用/冷恢复验收。每一层必须测试跨账号拒绝、旧任务绑定、准备中撤权和物理清理失败，之后才恢复业务插件。
