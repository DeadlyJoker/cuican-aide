## 产品定位与交付顺序

工作台围绕一个创作项目组织成果。用户能编辑创作需求、查看各阶段修订、生成单项素材，并追溯结果所用的输入和任务。Agent 负责准备创作内容和调用外部能力；平台继续承担授权、执行、审批、事件与恢复。

整体方向为“项目 → 分集剧本 → 角色/场景/道具 → 分镜 → 镜头生成 → 成片”。各阶段按实际能力开放。第一条项目闭环是“保存一版需求 → 确认概念图描述 → 调用现有 Krea2 插件 → 显式查询 → 将已核验图片引用关联到该修订”。这交付概念图，不声称已经制作短剧。

| 阶段                | 用户交付                                     | 接入条件                                                                |
| ------------------- | -------------------------------------------- | ----------------------------------------------------------------------- |
| S0 项目与概念图     | 需求修订、概念图生成记录、结果引用、修订对比 | 复用已接通的 Krea2 文生图；补齐项目索引及 UI 闭环                       |
| S1 大纲与分集剧本   | 结构化大纲、场次、动作、台词及用户确认       | 明确创作输出 schema、检查器与已发布 Agent；不从任意聊天文本自动认定成果 |
| S2 角色与场景资产   | 稳定资产 ID、参考图修订、上下游依赖          | 用户选定支持参考图输入的实际 API，验证一致性与结果归属                  |
| S3 分镜             | 镜头修订、剧本覆盖、引用的确切资产版本       | 明确业务镜头与供应商生成分段的映射，独立确定性校验                      |
| S4 视频、配音与合成 | 实际媒体结果和成片引用                       | 逐项选定并验证对应外部 API，按提交/查询/恢复协议接入                    |

不能先显示不可执行的“生成成片”操作。首版只开放 S0，其余阶段在项目概览中说明所需能力；用户可以保存创作需求，不能对尚未接通的能力付费提交。时间、同框人数或长宽比约束来自所选服务，不采用参考项目的数值作为平台通用规则。

## 入口与页面

已安装插件目录提供“短剧工作台”功能模块入口。设计创意场景在可用时提供快捷入口；首页仍保留原三场景、单 Agent 默认执行目标及任务输入，不增加第四场景，也不强制创建团队。工作台中的执行选择明确指向已准备的插件 Agent，不改变普通聊天的默认版本。

用户明确插件仅增加功能模块，不能替换整体页面。工作台应挂在现有 CrewON 界面内，保留原侧边栏、顶栏、导航和普通聊天入口；项目内容在模块中展示，交互预览也不能接管整页。

S0 使用三个页面层级：

| 页面       | 主要内容                                                     | 主要动作                                             |
| ---------- | ------------------------------------------------------------ | ---------------------------------------------------- |
| 项目列表   | 标题、最近编辑时间、当前需求版本、最近概念图记录             | 新建、打开、归档；列表分页，不一次加载全部任务       |
| 项目概览   | 当前创作需求、概念图区域、待确认成果、明确的能力可用状态     | 保存新需求版本、打开概念图、查看旧版本               |
| 概念图详情 | 用户确认的描述、源需求版本、生成记录、外部观察状态、图片引用 | 开始生成、查询原任务、打开会话、设为选用、生成新版本 |

宽屏用项目内容与详情并列；窄屏将详情作为可返回的独立视图。低高度时主要动作保持可见，内容区域滚动，避免把生成或查询按钮放进被裁切的底部。颜色、按钮、间距、焦点和弹窗沿用现有设计 token 与组件。

服务地址、配置修订与执行 Agent 放在项目外的“生成服务设置”。日常创作页只显示“可生成 / 需要配置 / 执行能力不可用”和可操作原因。内部 digest、私有端口与 token 不进入创作表单；确切执行身份由任务详情和服务端核验承担。

## 使用资格与独立积分

2026-10-02 用户明确：任何用户都可以使用插件，使用消耗独立积分。产品不增加企业或角色使用白名单；继续通过平台既有账号识别本次使用者和扣费主体，不要求用户额外提供身份信息来查看页面。开放插件使用不意味着开放服务配置修改，或允许读取其他用户的项目和积分账户。

积分按用户隔离，首轮按插件专用积分池建模，个人分别持有余额；以后是否与个人已有账户共用余额仍待确认。具体单价、计费单位、结算时机和失败退还规则尚未确定，实现不自行设定价格或默认互相代付。

后端已增加独立的 Domain 账本、Application 内部端口及 SQLite/PostgreSQL 显式迁移：账户按 tenant / principal / pool 隔离，支持入账、冻结报价、按实际额度结算、释放未结算冻结及有界流水。任务用例可注入服务端报价端口，冻结与原用户消息、history、Run、插件绑定及账务关联同事务提交；余额不足或后续写入失败整笔回滚。客户端不能指定付款人、额度或价格。重试返回原报价，换账号不能复用原付费回执。关联采用独立增量迁移，未配置报价的旧任务继续原路径。

生产装配尚未配置价格策略，未接入充值、公共积分 API 或自动结算，当前页面仍不实际扣费。任务完成不自动把冻结视为扣款，失败和受理不明也不自动退款；待单价、计费单位及结算规则确定后再接入。已验证的恢复只证明原生成费用不重复冻结，不代表生产多用户扣费已完成。

现有 `RunRateLimitSnapshot.credits` 是模型服务返回的余额快照，`ModelSpendingAccount` 是按 tenant/thread/goal 管理的模型费用预算，两者都不能作为已经交付的个人插件积分钱包。真实扣费须有服务端权威账户、余额及流水，在任务提交前核对余额和定价；同一次生成的幂等重放、查询与重连不得重复扣取其生成费用。模型调用或查询是否另计费用须由明确的计费规则决定。

受理未核实、供应商失败和取消应保持不同账务状态，按确定的结算规则处理，不能因查询失败便认定应退款或再次收费提交。页面余额、预估扣费和实际结算以服务端投影为准；当前交互预览未接入真实积分或扣费。该产品要求不表示多用户执行和扣费主体验证已经完成。

## 第一条用户流程

1. 新建项目，填写标题与创作需求。标题是检索元数据；题材、画面描述与风格属于创作输入。保存后得到第一版需求。
2. 在概念图区域填写或编辑生成描述，最多沿用当前插件的 2,000 字符限制。可由 Agent 提出描述草稿；草稿不触发生图，用户点击“开始生成”才创建任务。
3. 页面核对保存的输入与当前服务状态。没有匹配配置、已部署 Agent 或真实 readiness 时提供设置入口，保留输入并拒绝生成。服务准备继续沿原发布路径完成；本方案不假装保存 URL 已完成 Agent 部署。
4. 提交冻结需求版本、用户确认的描述和生成槽位，使用授权的既有 Thread，在同一事务中创建 Run、消息/history、不可变插件绑定及项目生成关联。需要新会话时先沿原线程创建及幂等协议完成，不能宣称 Thread 已包含在现有 Turn 事务内。提交后打开现有会话，复用审批与 SSE；原页面显示“调用中 / 已提交”，不提前显示图片已完成。
5. Agent 可在本次 Run 内查询；调用结束而外部仍在运行时，用户点击“查询原任务”创建关联原 operation 的查询 Run。刷新页面、打开项目、查看记录只读取持久化投影，不访问供应商。
6. 供应商状态确认为成功且结果引用通过原投影校验后，页面展示图片链接与观察时间，用户可以设为选用。图片不是自动取得永久有效的本地素材。
7. 编辑需求或描述创建新修订。旧生成保持原归属；新修订可显示“来自旧版需求”，用户显式生成新版本，不覆盖旧图，不自动再次提交。

当前工具仅接受 `prompt`。首版不提供未接通的参考图上传、尺寸、seed、画面数量、时长或视频参数控件。用户确认的业务描述作为原任务输入保存；模型实际提交的 prompt 与请求身份以真实工具执行/回执为依据，不能把业务描述冒充供应商的完整请求。

相同描述也可以显式生成一个新修订，但当前固定工作流不保证重做必然得到不同画面。一个 Run 可能包含多个 operation 或多张结果，采用操作必须选择确切的 operation 和图片，不能默认采用列表第一张；投影标记截断时不能声称结果已完整显示。

## 三类状态分别展示

| 状态        | 权威来源                     | 示例及含义                                                                              |
| ----------- | ---------------------------- | --------------------------------------------------------------------------------------- |
| 创作修订    | 项目服务的保存记录与依赖关系 | 草稿、已保存、已选用；输入依赖变化后显示需重新确认，旧结果仍保留                        |
| CrewON 调用 | 原 Run/事件                  | 执行中、等待审批、已结束、失败；“已结束”不表示媒体已生成                                |
| 外部任务    | 原 operation 的核验记录      | submitting、submitted、queued、running、succeeded、failed、unknownOutcome；显示观察时间 |

查询失败显示“本次查询失败”及已知的上次外部状态，不将供应商任务改成失败。`unknownOutcome` 显示“提交结果尚未核实，可按已保存标识查询；无法识别或历史缺失时需要人工核验”，不能把提交重试变成第二次生图。当前适配器可用原 correlation ID 查询 history/queue，但服务若忽略客户端指定 ID 且受理回复丢失，就不能保证找回实际任务；公开投影也未提供区分两类标识的 queryability 字段。停用后阻止新生成，原查询按既有授权继续；紧急撤销遵循原执行门禁。没有供应商取消接口时不展示“取消生成”，关闭页面也不宣称供应商作业已取消。

概念图可“设为选用”，这是用户的创作选择，不改变供应商状态或执行权限。S0 的“需重新确认”只针对与生成相关的输入依赖；重命名项目、调整列表排序不使图片过期。结果 URL 失效或无法打开不证明生成失败。当前 Krea2 对已经 succeeded/failed 的 operation 返回持久化终态，不再查询供应商，不能承诺查询会刷新失效链接；首版保留记录并如实显示引用不可用。以后只有供应商提供且适配器实际接通刷新机制，才展示“更新访问链接”。

## 业务数据与执行记录的关系

现有 `Thread.cwd` 和浏览器文件夹 roster 是会话/文件组织，尚无短剧项目或资产修订的服务端权威。现有 `ArtifactRecord` 只支持 text/plain 工具输出。新增项目数据放在既有 Domain / Application / Store 内，用 SQLite/PostgreSQL 的增量迁移实现，不复用 localStorage 作为权威，不把图片塞入文本 Artifact。

以下是 S0 数据设计，具体公共 DTO 与 schema 在实施时冻结并验证兼容性：

| 对象                  | 保存内容                                                                               | 不变量                                                             |
| --------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| CreativeProject       | 服务端 tenant/space、稳定 projectId、创建者、业务种类、标题、元数据 revision、归档状态 | 客户端不能指定 owner；重命名不改变创作输入身份                     |
| ProjectBriefRevision  | projectId、不可变 briefRevision、创作需求、内容摘要、创建者及时间                      | 追加修订，不覆盖；读取与写入均检查项目权限                         |
| ConceptAsset          | projectId、稳定 assetId、名称、用户选用的修订及预期 revision                           | 图片 URL 不是 assetId；选用指针显式更新                            |
| ConceptAssetRevision  | assetId、不可变 assetRevision、确切 briefRevision、用户确认的生成描述及摘要            | 一个修订对应一个明确生成意图；改输入必须产生新修订                 |
| ProjectGenerationLink | project/asset/revision、sourceThreadId、sourceRunId、源插件与不可变 binding 身份       | 与原任务准入同事务提交，不在 Run 启动后补关联                      |
| OperationResultLink   | 同一生成关联、服务端核验的原 operationId、结果索引与观察信息                           | 从持久化原 operation 枚举产生；客户端不能绑定任意 operation 或 URL |

当前实际存储已保存前四类对象及按 owner principal、审计 actor 和命令种类隔离的回执。ProjectGenerationLink 已通过显式内部增量迁移加入原 Run/个人积分冻结事务，原 binding 和任务回执 v0 保持不变；真实安装 source→target owner、Host dispatcher 和模块生成控件已接通。OperationResultLink、独立当前选用指针和不可变命令回执已通过增量迁移实现并验证；不修改原 ConceptAsset 的元数据 revision 或公共 shape；独立 7.0.0 页面控件已接入，当前指针单独读取，旧命令回执不覆盖新选择。

当前基础实现前四项的元数据、输入规则及实际双库存储：项目创建时由服务端账号派生个人归属，需求和概念图描述追加不可变修订，概念图冻结确切需求修订及摘要，所有写入使用显式预期版本。标题与资产名称最多 160 个 Unicode 字符，需求最多 8KiB UTF-8，生成描述按现有 Krea2 的 2,000 个 UTF-16 单元限制；公共协议已通过严格请求、投影和双库 HTTP 行为验证，响应限制为 60KiB，列表最多 50 项并按实际返回项继续分页。归档拒绝新创作，保留旧版本读取、重命名及恢复。版本编号承担修订顺序，系统时钟回拨不会被误作版本冲突。

Application 和可选 Control 装配要求明确注入当前访问策略与本人范围的 Store，未安装默认放行策略；未配置时不创建项目迁移或路由。生产装配继续要求真实 ProductionControlApiIdentity，本机管理身份不自动成为生产用户或付款人。实际 SQLite/PostgreSQL 适配器通过原宿主持有连接、显式独立迁移，创建项目与首版需求、其他元数据及输入修订均在一次事务中复核归属、预期版本、保存的需求并共同写入幂等回执。公共 DTO 省略 owner、tenant、space 与审计 actor。项目生成关联、原 Run 和积分冻结已同事务提交，已通过明确批准的安装包映射接入原公共 UI action 路径；已核验结果选用通过独立协议与同事务存储实现，客户端只指定确切 operation/revision/resultIndex，不提供任意 URL 关联。这里的输入修订不表示供应商已生成图片。

原 `ExtensionRunBinding` 继续保存配置修订与八字段目标；原 external operation 保存请求/动作摘要、供应商任务 ID、真实状态和结果引用。项目关联不复制密钥、私有 token 或整套启动环境，也不建立第二套执行状态机。查询 Run 引用原生成，结果更新原 operation；不会成为第二版概念图。

结果索引定位原 operation 持久化的 `images[]`，不能使用当前分页、排序或截断后的页面位置。采用命令需核对该原结果与预期 operation revision，不能因列表刷新而静默选中另一张图。

S0 的需求上限建议为 8KiB，标题 160 字符，生成描述沿现有 2,000 字符；单页最多 50 项。每次 Agent 工作只加载当前选定修订及必要摘要，后续最多显式选择 32 条依赖，不常驻加载整部小说或全部资产。单个模型可见注入片段继续小于 10K tokens。最终边界以协议测试冻结，不通过放宽原任务契约接入项目。

## 插件与宿主边界

短剧工作台的业务标识拟为 `crewon.short-drama`，承载项目、阶段成果、资产关系及可信视图。Krea2 的执行标识仍为 `crewon.comfyui-krea2`，承载现有生成配置、工具和 operation。首期按静态宿主装配建立这个明确映射，不增加运行时插件依赖解析器；业务入口与实际调用插件分别授权，不能以打开项目代替生成权限。

| 层                     | 新增职责                               | 继续复用                                                    |
| ---------------------- | -------------------------------------- | ----------------------------------------------------------- |
| Domain                 | 项目、需求/概念图修订、依赖与选用规则  | 原不可变插件和运行身份                                      |
| Application            | 当前身份的项目读写、生成准入、结果关联 | 原插件 readiness、任务授权、原 operation 与 Run 读取        |
| Store                  | 项目修订、业务关联及事务约束           | 原 Run/消息/history/插件绑定的事务配方与两数据库后端        |
| Control / BFF / Client | 有界项目命令及读取投影                 | 原 session、Origin、CSRF、幂等与错误分类                    |
| Worker                 | 明确阶段的有界指导和输出检查           | 原 AgentVersion / ToolBroker / Krea2 适配器，不重编核心循环 |
| UI                     | 已安装模块入口、项目/概念图视图        | 原会话导航、审批、任务状态与 SSE 恢复                       |

项目生成命令由 Control 解析业务归属，再使用同一插件任务准入用例；存储层使用受控业务关联的原子提交配方。不能采用“先调用任务 API、再补项目 ID”的两个独立写入。一般插件任务请求的未知字段校验保持不变，不给现有 DTO 偷加未定义的 projectId。该[内部扩展](./project-generation-link.md)、公开 Control/Host 生成动作及业务到执行插件的明确映射已接通，仍需逐项完成完整 S0 验收。

项目权限、源 Run 权限及原 operation 归属在服务端核对，并在异步 readiness/权限查询后提交前重核。所有命令保留预期 revision 与按当前 actor 隔离的幂等键；修改输入后重用旧键拒绝，丢失回复重试返回原任务与原业务关联。客户端保存中的临时状态不授予任务执行权。

S0 项目先限定创建者本人访问，并继续检查当前租户/空间及现有授权；同空间不自动获得项目读取或修改权限。团队共享需正式项目授权后再开放。已保存项目关联或选用指针也不绕过原 Run 读取权限、插件撤销或当前结果投影门禁。

归档只隐藏项目的新创作入口，保留原任务与结果读取；恢复是否允许新生成取决于当前权限和能力状态。S0 不添加级联物理删除或供应商全局取消，也不修改原团队及普通聊天记录。
