# CrewON 长程任务与连续运行可靠性方案

状态：实施中；已落地资源释放、流式批提交、内置适配器有效上下文读取、UI 局部渲染及正文缓存，并接通已投递通知和符合恢复条件的过期工具产物正文分批回收，详见第 12 节；全仓检查仍有已记录的失败，未通过 72 小时或 7 天连续运行验收。  
依据：2026-09-10 当前工作区代码、两份本机 SQLite 数据库只读统计及隔离复现。  
目标：同一逻辑任务持续数天，以及 App 连续使用数天、累计大量任务时，交互延迟和常驻内存保持稳定，故障后可以恢复；同时保持可复用的模型上下文，控制每个逻辑任务的模型总费用。

## 1. 保障范围与基本约束

- 活跃任务数、可见内容和正在处理的字节量决定热路径成本；历史总量不应决定每次输入、渲染、续跑和状态查询的成本。
- 保留现有 TypeScript、Node.js 24、pnpm 10、SQLite/PostgreSQL 架构。先复用现有 Worker、Store、Goal 和工作流持久化能力。
- 运行时权威状态、外部操作回执、用户历史不得作为普通缓存淘汰。缓存释放必须有明确的持久化确认或可重建依据。
- 原始历史继续追加；模型上下文通过带版本、可校验的投影读取。单个注入片段继续遵守 10K token 上限。
- 内存淘汰、磁盘分页和读取检查点不得改变模型可见的既有前缀。模型语义压缩独立决策，联合衡量正确性、上下文容量、缓存读写与整个任务的费用，详见第 11 节。
- 所有队列同时限制条数和字节数；每连接有界之外，还必须有进程总预算及并发准入。
- 支持持续运行不等于扩大用户授权的时间、token、费用或工具权限。续跑沿用累计预算，不能通过创建新 Run 重置预算。
- 需要分别验收窗口可见、窗口隐藏、渲染进程重载、Worker 重启和机器睡眠后恢复。机器睡眠期间不能保证本地执行继续推进。
- 当前关闭全部窗口会退出 App 并停止运行时。“关窗仍后台运行”需要显式产品语义及生命周期调整；本方案首先保证重启后恢复，不把当前行为描述为后台执行保障。

监听器复现使用从当前源码提取的等待函数，1,000 个真实 500 ms 等待结束后仍有 1,000 个监听器，abort 后归零；这不是完整 App 的 72 小时测试。常驻单个 Run 的 500 ms 轮询理论上可达到约 172,800 次/天，实际还受请求耗时影响。

本机两份数据库中，53,767 个文本片段正文共 455,751 字节；对应事件 JSON、指纹、回执结果和 outbox JSON 共 148,770,587 字节。该数值是逻辑字段统计，不代表物理写盘次数或可直接兑现的同等比例成本下降。

## 3. 长任务执行与上下文读取

### 3.1 有效上下文检查点

新增 Store 层的有效上下文读取接口，由应用层消费，避免 Worker 每次扫描全部历史。检查点至少绑定 tenant、thread、历史高水位、有效分支/回滚版本、投影算法版本及内容摘要。

读取内容为已有有效摘要、必须保留的用户指令、未结算工具关联和检查点之后的增量。读取检查点是现有有效投影的物化结果，创建或重建它不调用模型、不重新生成摘要、不改变消息或内容块边界。热窗口上限约束当前工作集，不得变成会话终身可拥有历史条数的上限；确需语义压缩时，在独立的安全边界决策并持久化新摘要。

不能仅查找序号最大的 compaction：rollback 可能使摘要无效，fork 可能保留旧分支。检查点更新与相关历史提交必须原子关联；读侧校验对应的历史头，版本冲突时重读，不向模型注入混合版本。

写入侧也必须去掉热路径中的 `#loadAllModelHistoryItems` 全量校验。通过历史头 CAS、唯一索引、有效分支信息、未闭合工具调用索引完成增量校验，不能简单跳过现有身份和顺序校验。

旧数据按有界分页建立检查点，支持中断续建，不在 App 启动时一次性把所有历史载入内存。历史全文、审计、跨检查点回滚属于独立分页读取路径。

### 3.2 任务推进独立于界面

同一逻辑任务由多个可恢复执行段组成，外层保存 Goal、工作流节点、累计预算、下一步和待确认操作。每个执行段有资源与执行预算，达到软边界时在已提交的助手或工具边界让出执行权。

Team 分配、节点依赖、人工审批等待及恢复计划持久化到现有应用/Store 调度能力。前端负责提交意图、展示、审批、取消；窗口隐藏、切换页面或渲染进程重载不能成为推进下一节点的必要条件。

默认 15 分钟的前端等待期限应改为“停止这次等待并展示当前权威状态”，不能据此推断任务失败，也不能自动新建重复运行。实际模型请求超时、工具执行超时、无进展检测、用户任务预算各自独立配置。

需要对单个 Worker 的串行 `#drain` 做公平性处理：在合法安全边界让出工作项，防止一个长任务占据全部执行机会。增加并发必须有进程与外部工具总预算，不能用无限并发掩盖排队。

## 4. 前端长时间交互

### 4.1 分页、缓存与渲染

- 会话列表仅保存轻量摘要；详情缓存与列表分离。列表筛选和搜索在服务端分页执行，不能先拉完所有会话再过滤。
- 首次打开会话只取最近一页，向上滚动才取更早内容。活动 Run 单独定位，不能依赖其恰好出现在历史列表第一页。
- 详情缓存按字节及数量淘汰。淘汰只丢可恢复的 UI 投影，不取消后台任务，不丢未提交输入、正在审批的状态或用户选择。
- Transcript 使用可变高度消息块的窗口化渲染。仅把可见块及少量预加载块挂载到 DOM；超长单条消息还需要块内分段。
- 完成的 Markdown 块复用渲染结果，只解析增长中的尾块。未闭合代码块、表格等达到预算后采用轻量展示，完成后按需格式化；不能悄悄丢弃正文。
- 流式正文放入局部状态，避免每个片段更新整个 App 和全部历史数组。历史工具卡、计划、变更账本按页加载，使用稳定实体标识更新。
- 用户正在编辑、选择文字或阅读旧记录时保持滚动锚点；虚拟化需要覆盖键盘、可访问性、复制、搜索定位和现有快照测试。

### 4.2 可见性与后台状态

当前前台流式节奏约 32 ms 一次。前台以交互预算自适应更新；页面隐藏时停止逐字动画与 Markdown 重算，仅合并状态。重新显示时从持久化消息/游标对齐，不播放几小时的积压动画。

运行完成的权威状态不应等待打字动画排空。将“后台已完成”和“可见正文尚在呈现”分离；追不上时直接对齐已提交正文。

详情缓存释放、浏览器预览回收和终端视图卸载都不应终止正在执行的任务或终端进程。预览仅在可恢复、无未保存交互且未固定时回收；活跃资源本身也计入准入预算。

### 4.3 终端增量输出

终端输出使用带递增 offset 的有界块缓冲。淘汰旧块只移动起始 offset，不改变进程 generation。已挂载 xterm 接收新 delta，并由自己的 scrollback 丢弃旧行。

只有进程更换、用户明确重置或重新挂载时才重放有界尾部。输出写入使用完成回调限制待写字节；通知文本也走同一字节上限。原始日志如需保留应写入有配额的日志存储，不塞进 React 字符串。

## 5. 资源预算与过载处理

以下为首轮压测候选值，不是现有实现或跨设备保证。以 16 GiB 内存、SSD、4 个受控活动任务和常规长文本/工具输出作为参考负载；8 GiB 设备降低并发和预览数量。真实构建、媒体处理等用户工具另行计入进程树预算。

| 资源                | 初始候选预算                                       | 达到预算后的行为                                            |
| ------------------- | -------------------------------------------------- | ----------------------------------------------------------- |
| UI 详情缓存         | 最近 3 个会话，正文和工具预览合计 32 MiB，任一先到 | 丢弃可重建的非前台详情；不删除会话                          |
| Transcript 渲染窗口 | 前后台合计约 100 个消息块，超长块再切片            | 按滚动窗口复用节点，旧内容分页                              |
| 模型传输待消费文本  | 每流 1 MiB 高水位、2 MiB 硬限；进程总量 16 MiB     | 高水位暂停接收，低水位恢复；总量超限限制新流                |
| WebSocket 消息      | 保留现有单帧校验，并另计解析对象、条数、总字节     | 不能通过大量小帧绕过总预算；超限进入明确可恢复错误          |
| 工具结果缓存        | 已持久化条目应归零；未确认结果进程预算初始 32 MiB  | 暂缓新调用，保留尚承担恢复职责的结果                        |
| 状态订阅            | 每窗口常驻 SSE 初始上限 4 条，后台状态聚合         | 释放非必要订阅，保留普通请求通道；所有聚合仍做租户/权限校验 |
| 健康连接下状态核对  | 每 15–30 秒加抖动，合并多个后台任务查询            | 完成与审批仍由事件即时通知；断线时自适应重连                |
| 流式事务批次        | 20–50 ms、32 条、64 KiB 任一先到                   | 单个已合法但较大事件可独立提交；关键边界立即 flush          |
| 清理批次            | 起始 100–500 行、单批事务目标不超过 50 ms          | 根据锁等待减小批次，交互繁忙或空间不足时调整策略            |
| 诊断记录            | 每 30 秒采样、按分钟聚合，保留 7 天并限制总大小    | 丢弃过期诊断，不丢业务事件；不默认持续生成 heap dump        |

字节计数是对象成本的近似，还需同时监测 heap、external/Buffer、RSS 和进程树。候选水位必须依据单帧大小、可恢复性与压测调整，不能宣称 2 MiB 字节计数等于 2 MiB 实际堆占用。

## 6. 写入效率、幂等与磁盘维护

### 6.1 一份权威内容与有界提交

执行指纹改为带算法/格式版本的固定长度摘要。旧字符串指纹继续可验证，新旧版本必须有混合读取、重放冲突和回滚升级测试。

先保留 canonical event 的原始顺序和编号，仅改变事务批次。一个批次更新一次当前快照、返回精简的内部追加确认，并产生一个事件范围通知。内部追加确认按事件身份、摘要和序列处理重复/重叠批次，不能依赖不可稳定复现的内存批次边界。

公共用户命令保留精确响应重放语义，不能用“读取现在的状态”冒充原命令的历史响应。原始历史不重写，SSE 仍在事务确认后发布；审批、工具外部效果、取消及终态边界之前必须刷入前序事件。

outbox 保持事务内可靠记录。消费端按序列范围批量读事件、发布和确认，预算要与 `RunEventHub` 的队列上限协调；不得一次灌入大批事件导致所有正常订阅者断线。

工具 Provider 缓存释放由持久化完成确认触发，并传递到组合/作用域/MCP 适配器。未确认、结果未知和租约失效路径不做普通 TTL 淘汰。恢复时先查权威回执，再决定是否协调；外部写操作结果未知时不得盲目重做。

### 6.2 分类保留

| 数据               | 回收前必须成立的条件                                                        |
| ------------------ | --------------------------------------------------------------------------- |
| 已投递 outbox      | 确认投递、超过配置恢复窗口、旧提交重放不会重新创建等价工作                  |
| 内部追加回执       | 对应执行已封闭，旧租约/旧序列会被拒绝或由精简记录识别                       |
| 公共命令回执       | 满足公开的重放契约；过期请求有明确结果，不能当作全新请求执行                |
| 原始消息、模型历史 | 遵循用户保留/删除规则，审计、fork、rollback 所需引用已处理                  |
| 工具产物           | 满足保留策略，已处理活跃/暂停任务的恢复引用；正文删除与元数据状态可重试协调 |
| 临时文件           | 不属于活跃写入者；超过崩溃恢复宽限期；启动后有界扫描                        |
| 缓存、普通日志     | 可再生成或不承担业务权威；有总大小、单文件轮转及过期策略                    |

原始历史可以随用户数据量增长，增长速度应可预测；已经失去业务用途的数据则必须在配置窗口内收敛。不能通过强制保留最近 N 条会话来实现稳定性。

清理仅使用现有持久化维护租约选出一个执行者，任务可重入、分批、有索引。禁止 App 启动时同步扫描整个数据库/产物目录。数据提交、取消与租约续期优先于统计和清理。

删除数据、释放数据库内部页和缩小数据库文件是不同阶段。空间整理应在经过备份和空间检查的维护窗口执行，不能作为每小时阻塞业务的操作。检查 WAL、空闲页、锁等待和剩余空间，先确认占用来源再处置。

磁盘接近耗尽时停止接纳会产生新状态的工作，保留现有回执和恢复空间。优先回收已明确可丢弃缓存；无法安全持久化时停止新的外部效果，保持 UI 可操作并展示权威状态。

## 7. 进程恢复与可取消等待

统一等待原语：正常完成、abort、异常、关闭都清理监听器和定时器；不得通过放宽最大监听器数隐藏问题。每项状态查询有超时与取消信号，同一任务最多一个在途核对请求。

重连和重启使用有上限的指数退避、抖动、并发合并及熔断。当前 Supervisor 已有退出重启，但还需区分异常退出、未响应和连续启动失败。不要用固定每日重启作为长程稳定性的验收方式。

Worker 退出时，以提交检查点和租约 epoch 为恢复依据；新 Worker 不能继承旧内存中的执行许可。子进程、MCP 连接和设备会话需要单独超时、退出与孤儿进程检测。

仅当恢复协议已验证时才允许因持续资源压力隔离/重建进程；未知外部结果必须保留并进入协调状态。Renderer 可以重建视图，不能重建一次新的业务操作。

## 8. 可观测性与验收标准

每个进程记录 heap/RSS/external、事件循环延迟、活动句柄/连接数、队列条数与字节、在途请求、重连/重启计数。数据库记录大小及增长率、表/索引占用、写事务次数、锁等待、outbox 最老未投递时间、维护进度。UI 记录输入/切换延迟、长任务、可见 DOM/消息块和缓存字节。

这些指标需要形成有总量限制的本地诊断包；采集本身不得频繁同步序列化全部会话或记录正文、密钥。

模型侧增加缓存字段报告覆盖率、按输入 token 加权的命中率、缓存写入量、首次输出延迟、重试/压缩费用和每逻辑任务总费用。按 Provider、模型及调用类型分组，避免将缺失字段当作未命中。验收同时包含整体成本和热请求命中率，具体口径与准入见第 11 节。

初始验收目标如下，必须在固定硬件、负载、数据集和版本下实测；性能目标未达成应阻止宣称“支持数天连续运行”。

| 项目             | 候选通过标准                                                                                                            |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 输入、点击、滚动 | 受控负载下交互 p95 < 100 ms；不得出现反复超过 1 秒的主线程阻塞                                                          |
| 切换已缓存会话   | p95 < 300 ms；首屏成本不随该会话总历史从 1 千增加到 10 万条而线性增长                                                   |
| 取消响应         | 控制 API 接受取消 p95 < 500 ms；之后不得启动新的外部副作用；在途取消按 Provider 能力确认                                |
| 72 小时内存      | 预热后在相同工作集、相同阶段比较，热缓存有平台期；每进程 GC 后存活堆增长 < 64 MiB 且趋势 < 1 MiB/小时，超过需解释并定位 |
| 总资源           | 16 GiB 参考机上受控 App 进程树 RSS 目标 < 2 GiB；外部真实工具另列预算，不用忽略子进程的方式达标                         |
| 历史规模         | 1 万会话摘要、同一会话 10 万条 canonical history、至少 100 万条运行事件仍能分页打开与继续执行                           |
| 连接/监听器      | 1 万次等待/取消/重连循环后回到同等活动负载的基线；不能随次数增长                                                        |
| 终端             | 连续输出超过 100 MiB 后缓存仍有界，新增输出不再触发全量尾部重放                                                         |
| 磁盘             | 输出单位字节的新增事件/回执/通知成本可测；暂停负载并经过回收窗口后，无用队列与临时产物停止增长                          |
| 正确性           | 断线恢复后已提交事件不缺失、不乱序；同一个幂等外部操作不被重复发起；未知结果不会被当作未执行                            |

生产环境不周期强制 GC。存活堆指标在受控测试中采集，生产主要观察内存平台、事件循环和资源压力；不能把 RSS 不立刻下降直接等同于泄漏。

## 9. 测试矩阵与降低验证成本

1. **快速边界测试**：等待监听器清理；缓存确认前后；重叠批次重放；历史跨 1,000/10,000 条边界；终端裁剪 offset；单帧及全局预算。
2. **真实用户路径集成**：从 UI 发起长任务，经过 API、SQLite/真实 PostgreSQL、Worker、MCP/设备模拟器和 SSE；覆盖组件现有视觉/快照。
3. **崩溃注入**：工具派发前、Provider 成功后但回执未提交、提交成功但响应丢失、outbox 发布后未确认、检查点提交与回滚、清理中断。
4. **24 小时压力**：混合大量短任务、单个长期逻辑任务、多工作流审批等待、持续终端输出、随机页面切换和连接闪断，快速暴露增长趋势。
5. **72 小时连续运行**：打开/隐藏窗口、后台长任务、长历史滚动、睡眠恢复、短时离线、限速网络、慢数据库和受控磁盘不足；执行过程不能靠定期重启清理内存。
6. **7 天候选版本验收**：冻结硬件与构建，保留资源曲线、故障记录、已提交事件校验结果和恢复报告；重启注入场景与不重启稳定性场景分别报告。

长时间高流量测试以确定性模型/工具模拟器为主，维持真实协议、长短片段、突发输出、工具结果和检查点，避免为耐久测试持续付出真实模型费用。另做小规模真实 Provider/MCP 冒烟验证，模拟测试不能替代真实连接行为验证。

模型缓存验证拆为无需模型费用的请求前缀回归，以及受预算限制的真实 Provider 冷/热请求对照。模拟器返回的缓存数字只能验证统计与预算逻辑，不能作为真实命中率证据。

加速次数测试与真实挂钟测试都需要：前者覆盖边界和大量操作，后者覆盖定时器、认证过期、睡眠、网络、长连接和日常维护。不能把一分钟运行十万次视为通过七天测试。

### 11.2 保持前缀与恢复状态稳定

区分四类状态：UI 详情缓存、Store 的有效上下文投影、Provider 会话续接状态、Provider 的提示词计算缓存。分别设置生命周期；释放前两者的内存时，从持久化数据重建相同的模型输入。

应用维护以下不变量：

1. 同一 AgentVersion、权限配置和协作模式下，instructions、治理上下文、工具描述、schema 和工具顺序稳定。相关模型设置也纳入请求配置版本；不得每次加载时按不稳定的发现顺序重排工具。
2. 当前时间、Run/segment 标识、预算余额和进度等动态内容按既有权限层级追加到后部，不改写历史消息，不把变化字段混入固定指令前部。不得为了缓存降低指令权限或继续使用已撤销的工具。
3. 已提交的消息、工具调用 ID、工具结果及内容块边界保持不变。磁盘批提交或 UI 文本合并不应改变下次模型输入的消息分段。
4. Provider 续接状态绑定租户、线程分支、模型/适配器身份和兼容的上下文配置。压缩、回滚、权限或模型切换确实使其不兼容时，显式失效并重建合法输入；不能为命中率跳过校验。恢复与手工历史回放需分别验证。
5. 不因切换页面、清理热缓存或生成新执行段而无必要地切换模型、重建 AgentVersion、改变工具集合。确有语义变化时记录原因，不把预期的缓存变化当作泄漏。

Provider 侧的可复用范围还受模型缓存边界与有效期影响，仅有客户端相同前缀不能证明实际命中；参数、断点和缓存写入统计应按能力配置。当前 OpenAI 指南分别说明了这些机制，不能把单一模型策略套用到全部 Responses 兼容服务。[OpenAI 缓存指南](https://developers.openai.com/api/docs/guides/prompt-caching)

`previous_response_id` 可减少客户端重复传输，但不能据此把历史输入按免费计费；OpenAI 的链式历史输入仍计入输入用量。[OpenAI 会话状态说明](https://developers.openai.com/api/docs/guides/conversation-state)

### 11.3 压缩时机和费用共同决策

读取检查点与语义压缩分离后，分页、重启、缓存淘汰不再成为重新调用摘要模型的理由。确需压缩时：

- 用模型实际输入容量约束，加上工具定义、治理片段、预留输出和下一次工具结果的空间；不能只用消息条数估计。
- 设置触发阈值与压缩后的目标区间，留出多个后续工具轮次的余量，避免刚压缩完下一轮又触发。具体区间按模型和工具负载测量，安全容量优先于缓存收益。
- 在没有未结算工具关联冲突的边界生成摘要，保存一次并复用；保留任务目标、用户约束、关键决策、待办和恢复所需证据。摘要来源和版本可追溯，不在每次读取时重新措辞。
- 同时比较“继续携带上下文的预计费用”和“摘要调用 + 新上下文首次处理/缓存写入 + 后续调用费用”，用实测复用次数估计收益；接近硬容量上限时不为省钱延迟必要压缩。
- 将语义压缩标为前缀变化事件，观察其后的恢复趋势。常规热请求与压缩后首请求分组，整体费用仍包含两者，避免通过排除冷请求美化成本。

优先选择不改变模型输入的资源优化：消除全历史扫描、释放已持久化的工具结果、UI 虚拟化、增量终端和批量存储。不要为了减少 App 内存而每轮摘要，也不要为了提高缓存比例无限携带无关上下文。

### 11.4 按 Provider 能力接入缓存策略

在现有传输适配器增加明确的能力配置，包含缓存读写用量的字段映射、缓存模式、有效期、断点支持及配置版本。未知网关保留已验证请求形状。云端 Agent 的内部提示词和模型调度由服务端控制，本地优化 `history` 不能证明其内部模型命中；服务端报告需区分单次调用与多次调用汇总，避免重复累计。

若配置缓存键，使用稳定、非敏感的租户/用户或工作区记账标识，必要时附 Agent 前缀版本；执行段 ID、随机数和当前时间不进入该键。键不替代身份授权，不能为共享缓存绕过租户或凭据隔离；是否按线程细分由隔离与记账需求决定。

对支持显式断点的 Provider，可以对照验证固定材料尾部与追加工具轮次边界的断点策略；需要同时观察缓存写入成本，不能简单在所有内容上加断点。多轮追加和一次性长材料使用不同的实验负载。不要为维持命中发付费空请求，也不为短提示词的统计比例添加无用文本。

缓存策略配置不隐式开启 `storeResponses`，也不自动延长服务端数据保留期限。长时间审批、离线和机器睡眠后允许出现冷请求，恢复正确性不能依赖缓存仍然存活。

### 11.5 用量、费用和预算口径

每次实际模型调用记录有界的用量摘要，并与逻辑任务、Run/segment/attempt 和 Provider 响应身份关联；内部重试、压缩和子任务都计入逻辑任务。事件重放按同一用量身份幂等聚合，不同时累加调用增量和 Run 累计快照；不能每个输出片段写一次完整用量回执。

建议保留输入、缓存读取、缓存写入、输出、用量来源、字段报告状态、调用类型、定价版本和首个输出耗时。字段缺失为 unknown，旧记录不凭补零推断完整覆盖；新增持久化/事件字段需要版本兼容与行为测试。

| 指标                    | 口径                                                                                                                        |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 已报告 token 缓存命中率 | 同一组有明确缓存报告的调用中，`Σ cachedInputTokens / Σ inputTokens`；分母为 0 时为不适用，不能平均每个请求的百分比          |
| 报告覆盖率              | 总调用中有用量报告的比例、已知输入 token 中有缓存报告的比例分别显示；缺失用量的调用单列                                     |
| 热请求表现              | 固定 Provider/模型/配置和负载，处于缓存有效期、满足可缓存条件的后续调用；同时列首次调用、压缩、模型切换和长时间空闲后的调用 |
| 任务总费用              | 所有尝试、压缩及子任务的实际已知计费之和；未知费用单列，不按 0 处理                                                         |
| 效率与质量              | 每完成任务总费用、成功率、首个输出 p50/p95、恢复耗时、压缩频率和上下文大小共同对照                                          |

适配器应先将不同 Provider 的用量归一为互不重叠的计费类别，再按对应模型/套餐与定价版本计价：普通输入、缓存读、缓存写、输出及已报告的其他收费项。不要把缓存写入在普通输入中保留后再全额相加，也不要把推理 token 在已包含它的输出里重复计费。实际公式取决于 Provider 的计费定义，未知字段不能据推测生成精确账单。

已有 Goal 的 token 预算继续按原契约展示；另设金额预算时，在模型调用/并行子任务启动前原子预留额度，收到实际用量后结算，不能靠续跑或重试重置预算。未确认是否计费的调用保留待核对状态，不能因为本地超时就把预留直接当作未消费；未报告用量按明确的保守策略限制后续支出。

监控维度只使用有界 Provider、模型和调用类型集合。任务 ID、用户 ID、缓存键和完整前缀不能成为无限增长的时序标签；诊断仅保存有期限和容量限制的摘要/指纹，不记录完整提示词。缓存命中不意味着可以放宽上下文、并发或用户费用上限。

### 11.6 验证与发布准入

1. **无需付费的请求回归**：固定同一持久化状态，比较前缀内容、顺序、内容块边界及相关配置；覆盖 UI 淘汰、Store 分页/检查点重建、Worker 重启、SSE 重连和批提交。非语义维护前后的既有模型输入应完全一致；该结果只证明客户端未破坏前缀。
2. **变化与恢复测试**：压缩、回滚、fork、权限/模式切换、模型切换及 Provider checkpoint 失效，分别验证合法失效和恢复；长序列工具调用与结果保持配对，必要的配置变更不能为缓存被隐藏。
3. **记账测试**：已报告零、缺失缓存字段、缓存写入、零输入、多层汇总、重试、流式中断后核对和压缩用量；验证加权比例、幂等累计、旧记录兼容及金额预算并发预留。
4. **受预算限制的真实对照**：固定 Provider/模型/配置/负载，在确认的缓存条件下比较首次与后续调用，以及压缩和恢复前后。真实缓存值来自 Provider，不能用本地字符串相同比例替代；不为本设计分析自动发起付费实验。
5. **候选发布门槛**：固定负载先建立基线；每组至少 100 个可观测热请求作为初筛，样本不足或波动较大时不宣布通过。非语义维护不得改变前缀；热请求加权命中率下降超过 5 个百分点触发调查，最终判断还需看样本波动和重复对照。
6. **联合验收**：在同等任务质量与成功率下，每逻辑任务费用和首个输出延迟不得出现未解释回退；72 小时和 7 天同时记录缓存与费用曲线。压缩导致命中率降低但总费用下降时，可以凭明确的正确性和成本证据接受；不能只追求统一的 90%/95% 命中率。

优先实施可信统计与前缀回归，再对照调整压缩和 Provider 配置。这些工作复用现有模型适配器、用量事件和预算域模型，不新增常驻“缓存服务”，也不把全量提示词复制进第二份诊断存储。

### 12.11 第十一批：已投递通知分批回收，2026-09-11

- **接入实际通知调度**：Outbox Dispatcher 在正常投递之外管理一个独立、可关闭的维护任务。默认仅回收投递确认已满 24 小时的通知，每 10 秒最多处理 100 条；有投递正在进行时先让出本次机会。同一维护器最多一个在途批次，退出时取消 timer 并等待已有批次结束，维护失败单独记录，不覆盖投递状态。内置 SQLite、PostgreSQL 和 InMemory 均已接入；旧自定义适配器未实现可选端口时保持原有行为。
- **保留去重与业务引用**：新增独立消息身份表，保留 `messageId/tenantId/runId`。新通知在同一业务事务内注册身份，旧通知在回收时补注册；数据库触发器拒绝身份复用及身份列改写。这样删除队列行后，旧命令仍返回原始回执，不会重新投递，新的冲突命令也不能复用旧 ID。自动化调用的重放校验实际依赖初始通知正文，因此仅将被其持久化回执明确引用的通知正文保留为独立重放依据，其余身份记录不保留正文。原有自动化完整校验仍执行，损坏的保留正文仍会导致拒绝重放。
- **事务与维护节奏**：身份保留、通知删除和下一次维护时间在同一短事务中提交。共享数据库的多个执行者通过单行维护状态竞争，不能各自重复消耗完整清理批次。SQLite 不等待前台写锁，忙时跳过，并恢复原连接的 busy timeout；PostgreSQL 使用数据库时间、1 ms 锁等待上限和 `SKIP LOCKED` 跳过锁定行。崩溃/异常回滚同时恢复队列、身份记录和维护时间，不会出现先删正文再补去重的空窗。
- **索引与范围**：SQLite 查询明确使用按投递完成时间排列的部分索引；测试发现仅新建索引不足以阻止优化器选择旧索引并做额外排序。PostgreSQL 使用单语句固定的数据库时间作为截止条件，使其可成为索引范围条件。候选查询只将最多一批消息 ID 返回 JS，正文保留在 SQL 内处理；没有扫描目录、加载历史正文或执行 VACUUM。原始事件、模型历史、公开命令回执、执行队列与未投递/租约中的通知均保留。

### 12.12 第十二批：本地磁盘水位准入及恢复，2026-09-11

本批把本地磁盘容量检查接到实际 Control API、后台自动化调度和 Worker 执行入口。目标是在剩余空间不足时减少新增工作，同时保留取消、回执结算和已有通知维护的通道。它是准入保护，不是磁盘配额或空间预留，不能保证其他进程继续写盘时仍有足够空间完成事务。

- **有界探测**：默认可用空间低于 1 GiB 时阻止新增工作，恢复到至少 2 GiB 才重新放行；两个阈值用于避免水位附近反复开关。读取 `statfs.bavail × bsize`，以配置路径中的最低可用空间为准，每个实例最多 8 个路径、一组在途探测，结果复用 1 秒。探测超过 2 秒或结果无效时返回容量未知并停止放行；超时的原生调用仍占用原在途位置，不能靠超时不断堆积新的文件系统调用。迟到的探测结果不会恢复准入。关闭时释放 timer 和等待者；无法取消的原生调用仍须等待操作系统返回。
- **执行边界**：Worker 在新模型尝试、上下文压缩、新工具回执/尝试以及实际工具派发前检查容量。压力异常只重新安排原 Work Item，默认 30 秒后重试，不创建失败的模型尝试、不重新生成上下文。尚未派发的工具在恢复尝试写入前也检查容量，避免压力轮询持续增加尝试记录。取消所需的终态记账、已经派发操作的 reconcile/结算不使用这个准入条件。
- **工具批次**：派发标记移到各工具真正调用之前；串行批次遇到失败不启动后续调用，并先持久化成功前缀、确认其结果释放，再处理失败。并行批次等待所有已启动调用返回后再处理错误，避免仍有调用运行时提前释放 Worker 租约。为保留结果顺序，首个失败之后已成功的并行结果仍交由 Provider 保留与后续 reconcile，不在本批承诺所有结果立即回收。
- **请求和后台入口**：Control API 的新增变更返回既有错误信封格式的 HTTP 503，错误码为 `storage_capacity_low` 或 `storage_capacity_unknown`，携带 `Retry-After`。GET/HEAD/OPTIONS、取消 Run、清除 Goal、拒绝审批、工作区操作 cancel/reconcile 继续经过原有鉴权、版本及幂等检查。例外按已注册的路由模板判断，不通过用户 URL 子串匹配。自动化调度在扫描前及每次入队前共用同一检查，空间不足时停止当前批次，不继续生成新的后台 Run；恢复保留原 occurrence 幂等键。正在进行的业务写入和通知回收不因水位变化主动中断。

组合配置新增可选 `storageAdmission` 端口及 `localStoragePaths`。SQLite 组合自动检查数据库路径；两个程序入口还加入产物目录和产物索引数据库。显式传入的端口由调用方管理生命周期。`:memory:` 且未配置本地路径时不建立文件系统探测器。PostgreSQL 组合仅能检查显式配置的本地路径，不能从 Worker 所在机器推断远程数据库的剩余容量；远端数据库水位仍需独立信号接入。没有修改数据库 schema、HTTP 数据形状、模型配置或缓存键。

### 12.13 第十三批：工具轮原子提交及增量模型续接，2026-09-11

### 12.14 第十四批：失效检查点的有界恢复，2026-09-11

### 12.17 第十七批：工具结果容量预留与 Worker 唤醒合并，2026-09-11

### 12.20 第二十批：异常写工具的持久化防重与核对退避，2026-09-11

已确认两类相互关联的积累：写工具抛出异常后，Broker 保留拒绝的 Promise，恢复仍得到同一异常，无法把防重记录转交 Store；而结果进入核对后，原实现按固定间隔创建新 Attempt。单纯释放内存会丢失防重依据，单纯转入核对又会增加磁盘写入，因此本批同时处理结果归属和重试频率。

- **异常归属**：仅对 mutation + reconcilable，把已分派工具的异常暴露为恢复专用的 unknownOutcome。直接 execute 仍返回原拒绝 Promise；同一操作不能通过恢复重复执行。错误仅保留有界代码，核对和取消共享可持久化的未知结果，纯元数据查询也能发现它。只有 Store 已提交、执行身份与动作摘要匹配的 unknownOutcome 确认才能释放该内存记录。没有把异常伪造成成功，也没有给只读工具扩大确认权限。
- **持久化退避**：核对返回未知和核对 Provider 抛错均按已有 Tool Step/Attempt 次数增长间隔，重启不重置计数。默认基础间隔 1 秒，后续指数增长至 5 分钟；显式配置为 0 保留原有无等待语义，显式更慢的基础间隔不会被缩短。稳定期每个持续未知操作理论上约 288 次核对/天，低于每秒核对的 86,400 次/天；这是调度上限的推算，不是实际挂钟测量，Attempt 数据仍会增长。
- **取消竞态**：取消事件与解除等待在同一 Store 提交中完成。仅经当前核对回执的主键定位对应 Work Item，再校验 tenant/run；没有扫描全部任务或新增索引。复用私有队列原因字段保存一次性取消唤醒标记，claim 消费标记；若取消发生在已领取期间，retry 消费标记并立即放回队列。不会替换租约，也不会因重复取消回放形成零间隔循环。SQLite/InMemory/PostgreSQL 行为一致；旧字段及公开事件形状不变，旧实现不识别该标记时只会沿用其重试间隔。已进入取消模式的核对不再启动会中止自身的 CancellationWatcher，租约心跳仍保留。
- **确认失败**：未知结果的事务一旦提交，Work Item 已被重新排期。此后 ACK 失败只返回待修复状态，不再使用旧租约进行第二次 retry；下一次领取修复确认。
- **模型缓存**：这条维护路径不新增模型调用、不注入维护计数、不改写历史。实际 HTTP 测试对比正常执行和异常恢复的完整请求，结果相同，保留 previous_response_id 与增量 function_call_output。

### 12.22 第二十二批：桌面子进程日志背压与重启边界，2026-09-11

已确认 `RuntimeSupervisor` 对 Control API、Runtime Worker 和发布子进程的每个 stdout/stderr 片段直接调用父进程标准流 write，忽略写入完成与背压。隔离复现向阻塞的 Writable 转发 2,000 个 64 KiB 片段，131,072,000 字节正文留下 131,106,000 字节待写缓存，增长随日志量变化。

- **统一容量**：同一 Supervisor 的所有子进程共享 stdout/stderr 两个转发器。每个方向最多排队 128 KiB、64 块，每块和唯一在途写入最多 16 KiB；两方向排队及在途正文合计上限为 288 KiB。源数据按有界片段复制，不能用小 view 留住大 Buffer；UTF-8 跨源片段解码只保留未完成字符。该数字不包含 Node 上游管道、转换瞬时内存、对象或分配器开销，也不是整个进程的内存上限。
- **过载处理**：目的流写回调完成前不追加第二笔写入，不依赖目标的 highWaterMark 大小。超额日志淘汰旧片段、保留近期尾部；恢复后报告丢弃量，并在持续过载时让提示与实际尾部交替，避免只输出提示。继续读取子进程的诊断管道，不以暂停日志读取阻塞后台工作。持久化 Run、工具回执、模型流和 MCP 协议输出不经过这个丢弃通道。
- **启停与故障**：重启复用同一转发器，不给仍未完成的写入再开一套缓冲。stop 释放待写尾部与已排程工作，不等待堵塞日志；每个已提交到目的流的在途片段仍由该流持有，直到完成或进程退出。源进程 close 后移除本次监听器；正常写入结束并停止后移除目的监听器。失败目标停止新写入，保留一个错误处理器覆盖回调后的 error 事件，不随重启累积错误处理器。新增只含计数的 `logStatus()`，尚未接入用户界面或长期指标包。
- **成本与磁盘边界**：本批不增加后台进程、日志文件、模型请求或提示词内容。没有改变标准流的外部保存策略；用户若把 stdout 重定向到无限增长的文件，仍需独立轮转。曾验证直接使用文件描述符异步写入，但真实堵塞管道会拖延进程退出，因此未采用。当前标准流在部分系统的 TTY 或文件目的地仍可能同步阻塞；本批约束排队内存，不能承诺这些目的地的写入时延。

新增 10 项测试：2,000 大片段和 100,000 小片段的容量边界；大 Buffer 不被切片引用保留；UTF-8；1,000 次堵塞重启仅保留原写回调；错误目标；1,000 次源绑定/释放；真实子进程在两方向堵塞时仍完成 128 MiB 输出并通过独立 IPC 回报；真实标准管道不被读取时仍响应 ping 并正常退出；实际 Supervisor 使用隔离模拟服务连续 5 次启动/重启，每次产生 32 MiB 日志，HTTP 保持可用、10 个子进程最终全部退出，模型 ID、AgentVersion 和 profile 内容保持相同。

其中隔离 GC 子进程先预热 1,000 个片段，再处理 5,000 个 64 KiB 片段及 4 个 20 MiB 输入。断言 GC 后存活堆增量小于 4 MiB、ArrayBuffer 增量小于 2 MiB，并验证清理后释放；这是单组件的操作次数压力证据，不是 72 小时内存趋势或真实 Provider 缓存证据。生产没有强制 GC。

桌面/UI 全套 379 个测试文件、2,471 项通过，UI/Electron 类型检查、桌面宿主构建及 TypeScript 入口边界通过。文档格式和差异空白检查通过；实际子进程测试均等到 close，Supervisor 测试复核子进程已退出，专用临时目录已清空。未运行付费模型探测，未修改全仓既有架构失败的允许列表。

### 12.26 第二十六批：摘要超限恢复预算与前缀保护，2026-09-11

- **治理前缀保护**：内部 `ContextCompactionContract` 增加可选 `protectedPrefixLength`，Worker 标明治理消息前缀，内置 compactor 在每次恢复中逐字保留其中的 trusted/untrusted 内容、角色与顺序。旧调用方默认 0；未标注的 system/developer 消息也不能被删除。非法长度或包含工具项的前缀在调用模型前拒绝。该元数据不进入 Provider 请求，不修改 HTTP 或持久化格式。
- **完整工具边界与取消**：沿用最早源历史的恢复策略，但工具调用必须连同其完整结果一起跨过；并行交错工具批次不会产生孤立结果。不能跨过 system/developer 指令，也不能删除最后一段源历史后生成“成功”的空来源摘要。初始来源为空或只有治理前缀时不调用模型；调用前、错误后和下一次恢复前检查取消。
- **失败与恢复语义**：超出次数、没有可安全裁剪的源边界或无法继续缩小时，保留原超限错误。Worker 按现有非重试错误路径结束本次 Run，不提交 `context.compacted`；原始消息和模型历史保持不变。SQLite 与真实 PostgreSQL 集成测试检查了 1 条、20 条来源、成功恢复、用量持久化及重启后不重复请求。已有 AR-025 两条普通消息、第一次失败后删除最早一条并成功的行为仍通过；原先“只剩摘要提示词也可成功”被明确禁止。
- **缓存与用量口径**：普通成功首请求保持原样；只有真实语义压缩的超限恢复会调整来源，不通过 UI 缓存清理或 Store 维护触发这一流程。集成测试逐项比较治理前缀及 instructions，确认恢复没有改变它们。失败尝试的已报告用量继续单独持久化；模拟的两次输入各 100 token、缓存读分别 0/80，整体加权命中率为 40%，不会只展示最后成功请求的 80%。这不是 Provider 真实命中实验，缺失用量、缓存写入和金额预算仍未补齐。

**仍需处理的语义与成本边界**：既有 Worker 在进入 compactor 前仍使用 `boundedContextTail`，超限恢复仍可能移除旧源内容。本批不是覆盖全部来源的分段摘要，也不保证 4 次之内一定适配任意 Provider 窗口；较大的窗口配置偏差将明确失败，而不是无限尝试。后续需要提前按实际输入容量预留余量、在完整工具边界分段、保存可恢复摘要进度，并将所有中间调用纳入逻辑任务费用，不能简单加快删除旧消息或把所有摘要用量当作最终上下文大小。

### 12.30 第三十批：App 流式预览工作集、后台暂停与安全收尾，2026-09-11

### 12.37 第三十七批：命令后代回收与 MCP 请求生命周期，2026-09-11

修复上一批真实 MCP 取消试验暴露的命令残留，并处理验证中发现的 SDK 请求计时器和监听器残留。继续使用 Node 24；命令监护逻辑随原 MCP 入口一起打包，不新增安装依赖、后台常驻服务或独立构建体系。

- **命令所有权**：每个活动的 Git/UI 测试命令由一个短命 Node 进程管理，在 POSIX 下作为独立进程组的存活锚点。MCP 通过专属输入管道维持所有权，显式取消或 MCP 意外退出导致管道关闭，监护进程仍能回收该组。正常命令退出也回收后代；取消/两分钟超时先发 SIGTERM，200 ms 后强制终止。父层还处理监护进程独立意外死亡、后代持有输出管道等情形，不能只等 `close` 事件。每个 MCP 进程最多 4 个活动命令，没有等待队列，关闭会取消全部；清理无法确认则拒绝继续接纳命令。

### 12.40 第四十批：桌面 HTTP 按需读取与共享准入，2026-09-11

针对第 12.39 节已复现的未消费流积累，桌面 HTTP 改为内部 v2 拉取协议：主进程只返回响应元数据，渲染层 `ReadableStream` 的 highWaterMark 为 0，只有消费者发起读取才请求下一块。Node/Electron 的原生 fetch 使用 BYOB reader，在读取前分配有界缓冲，普通响应每次最多 64 KiB，SSE 每次最多 8 KiB；返回实际字节副本，避免为很短的事件复制整份 BYOB 缓冲。原每请求 IPC body 监听器、元数据之前的 pendingBodyEvents 和后台推送循环均已移除。

| ---------- | ------------------------------------------------------------------------------------------------------------------ |
