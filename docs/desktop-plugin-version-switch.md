# 桌面插件版本切换

2026-10-07，实际 Short26 → Short31 升级验收发现：设置页直接以启用状态切换版本，而原生业务执行要求先停用并配置已选择的候选版本。拒绝被误报成普通版本冲突，刷新不能解决。

修复保留原生执行的准备与权限校验：桌面管理版本页面先明确停用旧版，再由用户选择新版。新版保持停用，完成原有业务配置后才能启用。Web 和旧版桌面桥接沿用原有版本选择行为。

Main 允许选择尚未配置的停用版本，但先后读取原有业务激活状态，确认它没有启用；提交后再次核对实际选择。旧版本运行时不会用自己的配置激活新摘要。未停用、并发激活、选择变化和运行时撤销均不返回成功。原请求的幂等键和未知结果恢复机制保持原样。

设置页新增流程快照及行为验证，Main 测试使用真实类型客户端、原生运行时所有权和具名 HTTP 响应夹具。此类测试不代替打包 App 的实际升级验收。

原始复现与正常退出备份：`output/extensions/checks/native-short31-20261007/`。正式安装的 App、用户数据和冻结插件包未修改。候选版后续实际验收仍需完成升级配置、项目读取、重启恢复及真实 ComfyUI 闭环。

实际新版执行准备还暴露了多版本批准的兼容问题：批准表按包保留历史版本，准备配置却要求每个插件只有一个条目。Main 现按插件合并准备条目，保留全部精确包批准；同插件任一保留版本要求逐次批准时采用该更严格要求。测试直接将 Main 发出的配置交给 Worker 的真实解析器，覆盖新旧版本顺序和批准要求，避免重复条目导致整个本机环境启动失败。

后续启动校验还把保留的历史生成、查询映射误当成必须准备的当前版本。现在启动时按原生批准表校验映射目标；提交执行时同时要求精确的插件、发布者、版本和包摘要已经批准并在本次运行时准备完成。原有已启用选择、业务配置、请求身份及提交时所有权校验继续生效。读取已批准旧包不会授予它执行权限。

此修复不改写批准文件、历史映射或项目数据，也不改变协议及持久化格式。回归使用实际文件批准、两个真实校验包、原始 SQLite 和具名离线执行准备响应，覆盖两版本启动、当前版本提交、旧版读取与执行拒绝、未批准来源及目标摘要拒绝。保留历史记录不表示旧版任务可自动恢复执行；历史执行仍须通过其独立的目标准备与权限校验。

启用参考图工作流后，候选准备及发布 CLI 也必须等待媒体能力的异步初始化。三个发布入口现在统一使用原有异步 Worker 准备接口，传入同一份宿主存储配置，并在失败或取消时关闭已获得的所有权。它只读取已安装工作流并验证摘要，不导入插件 Node 入口、不调用模型或生成服务。测试覆盖 v1/v2 候选准备、实际发布加载器以及工作流和清单摘要变化时不发布输出。

桌面启动顺序是先 Worker、后 Control，因此首次启用图片结果能力不能依赖 Control 预先建好结果表。原生 Worker 在明确获批结果发布且启用资产 v2 的情况下，先在原数据库初始化空结果表，再提供只读结果读取器；只有读取批准时仍要求已有有效表结构，不推导写入权限。此过程不创建任务、图片或采纳记录，Control 后续继续使用同一结构并校验其完整性。
