# 对话发送与流式输出恢复（2026-10-10）

## 复现证据

Web 验收使用已有管理员登录、配置的网关 API Key 和真实 `gpt-6.1-sol`，没有绕过账号验证，也没有安装业务插件。

会话 `01a123e3-1018-72bb-8b37-c166351742a8` 的 Run `01a123e3-1258-7723-aefd-e221051715df` 在 03:37:26.359Z 创建、03:37:43.349Z 完成，约 17 秒。后台保存了 8 个文字增量和 85 字正文；15 个事件的 outbox 都投递一次成功，末次投递为 03:37:43.519Z。直接读取本地 Run SSE 回放耗时 36 毫秒。页面仍长时间显示“正在思考”，不能把这段等待计入模型执行时间。

当时 Vite 上存在 5 个长时间未结束的资源目录代理连接以及 Thread SSE；目录读取没有超时，组件销毁只忽略返回结果、不取消 HTTP，重复挂载又发起整组请求。浏览器连接被占用，使实际 Run SSE 和后续 GET 排队。

另一个独立问题是终态处理等待完整会话回读：正式正文、工具历史、计划及额外快照串联在结束路径上。回读超时后再进入同步重试，页面继续显示执行中。可信执行终态、正式消息同步和可选详情恢复原先没有明确分开。

## 修复边界

- 发送处理先创建有界本地用户消息，再等待网络；正式确认后去重替换。提交失败保留明确失败状态和草稿恢复，不伪造 Run 或正式消息标识。
- 新会话返回时先绑定本地提交，再发布会话选择，避免已切换到新会话而本地消息仍属于草稿的空窗。临时消息由实际 Transcript 的可见 Run row 认领，不能因为全局 Thread 缓存已有 user item 就提前清除；正式消息完成渲染后才确认移除。
- 仅有正式消息标识或空正文仍不能接替本地消息，纯图片输入也需要有可见内容。团队进度通过本地 submission ID 与同一次提交交接，避免准备阶段显示两个用户气泡；该标识不进入 HTTP、模型请求或持久化。
- 供应商文字缓冲保留原字节阈值并增加 50 毫秒刷新窗口；UI 每 32 毫秒显示整批已收到文本，去掉固定逐字播放造成的人工延迟。
- Control SSE 在写入背压时等待 `drain`，关闭或取消后释放监听器，保留身份校验及事件顺序。
- 资源目录读取由当前账号和组件生命周期持有。相同账号仅共享进行中的读取，最后一个订阅者离开会真正取消；账号换代立即取消并拒绝旧结果。完成后不保留目录缓存。
- 目录的 2 个物理读取槽、单项 10 秒和整组 45 秒期限用于保护连接预算；取消、请求去重和所有权修复才是消除重复挂起请求的关键，不通过限制会话并行掩盖问题。
- 可信 Run 终态立即更新对应轮次并释放实时 reader；正式消息同步独立恢复，只重试读取、不重启模型执行。正式正文通过 Thread 身份、版本及输出标识校验；工具和计划详情不再阻塞正文。
- 正式消息尚未同步时，编辑重放保持关闭；允许继续发送，但已收到的上一轮回复必须按 Run 保留。晚到结果只更新对应旧轮次，不能覆盖后继运行。
- 模型 HTTP 在正式终态通过身份、正文和用量校验后，先检查同一次读取中已经收到的尾帧，再结束读取；仍拒绝终态后的违规帧。未收到终态、无效终态和完整文字不能冒充成功。正常 EOF 保留连接，未关闭的尾流主动取消；底层取消 Promise 不完成或拒绝也不能阻塞已验证的结束事件。

可信终态后的 HTTP 生命周期缺陷用保持连接开放的真实本地 HTTP 和 Kernel 集成确定复现：旧实现已经产生 completed，却随后因尾流 idle 超时重试模型。新实现证明仅发起一次模型请求。这是另一个独立本地缺陷；本轮真实外部缺终态的请求没有触发它，不能用这项修复宣称网关问题已解决。`httpTiming.streamEndMs` 的字段及持久化形状保持兼容，其含义是客户端拥有的读取结束，包括正常 EOF 或可信终态后的主动关闭，不再必然表示远端 EOF。

相同配置下，`gpt-6.1-sol` 的最小请求和带正式工具定义的请求已完成；`gpt-6-astra` 的 Lite 和 Standard 两种请求均由上游返回 `server_is_overloaded`。这证明当前 overload 不是仅由本地 Lite 配置触发，不应禁用整个 GPT-6 系列或自动换模型。

本次同一会话的第二轮 Run `01a123fe-d90c-7318-a522-aa30766cadaa` 再次复现 `invalid_prompt`。第一采样响应头 28.203 秒、首字 52.300 秒，文字后 60 秒无字节，触发原有 idle 重试；第二采样响应头 7.986 秒、首字 10.204 秒，在 13.589 秒收到失败终态。重试前已有 90 字，重试后有 102 字，不能伪装成正式成功回复。

离线重建原请求为三条短的 user/assistant/user 消息、三个基础工具（get_goal/create_goal/update_plan）、无 instructions、无 previous_response_id。直接调用同一网关、同一 API Key，绕过 UI、Control API、Worker 和 Kernel 重试，单次 55 秒截止：HTTP 200，2.054 秒响应头，14.729 秒首字，84 个原始 SSE 事件、91 字文字，但没有收到正式终态；未使用 HTTP 压缩。因截止前没有终态，本次不能证明此前 invalid_prompt 的具体参数原因，只能排除“仅由 CrewON 页面或任务排队导致迟延”。

历史错误未保存上游具体参数消息，当前单次探测也没有返回错误参数；仍需对照网关侧同一请求的执行和最终流事件，不能声称这类错误已经修复。去掉 Lite 独有参数、保持相同三条消息和三个工具的 Standard 对照请求，在 10.548 秒响应头之前发生 `responses_transport_unavailable`，没有获得 HTTP 响应，因此不能据此更换生产请求 profile。

随后不带鉴权直连公开 `/v1/models`，也在 10.562 秒发生 `UND_ERR_CONNECT_TIMEOUT`，浏览器网关首页同样连接失败。这不涉及模型执行，说明当时另有公共 HTTPS 建连问题；不能将所有耗时归因于模型推理或本地排队。
