# CrewON 交付与示教能力路线

决策日期：2026-09-14。状态：产品方向与首版范围已确定；本文不代表功能已实现或需求已通过用户验证。

## 产品决策

CrewON 优先建设通用工作执行与交付能力，在跨行业的重复流程上验证深度。用户通过提供模板、录制示范和修正结果，让 AI 学会自己的工作方法；业务规则沉淀为 Skill。

本轮决定的顺序为：交付基础 → 录制生成 Skill → Skill 接入现有日程安排。定时重复执行复用现有日程入口与调度能力；成功任务保存为 Skill、成品模板、人工接管和批量执行根据验证结果逐项加入。

日程接入的新增范围是让用户从 Skill 选择“添加到日程”，带入技能版本、输入参数和交付位置，复用日程的执行时间、运行记录与状态展示。运行前检查所需工具与授权；技能升级后的版本切换明确处理。上述技能绑定仍需实现与验收，不能把现有日程可执行 prompt 等同于已支持版本化 Skill。立即再次执行保留在任务或 Skill 入口；批量处理解决一组输入的逐项状态与失败重跑，可由同一日程触发，不新增调度系统。

首批目标用户按工作行为选择：每周需要从文件或业务后台收集数据，按固定口径加工，再按固定模板交付给同事或客户的桌面用户。运营、行政、销售支持和项目协调都是招募来源，不分别建设行业产品。

第一条完整流程定为：**多份表格 + 用户现有模板 → 可核对、可编辑的汇总文件 → 定向修改并保存 → 下次换材料复用。** 第一阶段使用用户主动提供的文件；第二阶段用浏览器示教接上后台取数与下载。

## 第一阶段：完成文件交付循环

### 首版范围

1. 接收多份 CSV/XLSX 和一份用户指定的 XLSX 模板，明确工作表、数据范围与处理规则。需要补充的业务口径集中提出。
2. 保留原始材料，完整数据由受控文件工具分批读取；模型上下文保持有界，不通过扩大文本注入上限实现大文件支持。
3. 生成独立的 XLSX 交付文件，提供预览、下载或本地打开，清楚显示名称、版本、生成状态和对应任务。
4. 检查行数、合计、排除规则、缺失字段和公式错误，附可追溯的异常清单。未确定的值保持未知。
5. 用户能够指定工作表、列或单元格范围继续修改；修改前核对文件版本，遇到用户已修改的内容时明确处理冲突。
6. 再次打开任务能找到相同版本的文件与检查结果；修改生成新版本，不覆盖用户原始输入。失败后可以定位问题并保留已交付版本。

首版需要明确支持范围与文件大小上限。宏、复杂透视表、外部链接及特殊格式的支持必须逐项验证；不能对未验证模板承诺完整保持。Word、PPT 后续按同一交付循环扩展，避免把所有格式一次纳入首版验收。

### 必测材料

- 多个表结构相同，跨工作表汇总，检查无遗漏、无重复。
- 表头不同、空字段、重复业务编号、币种混合，要求保留冲突供用户处理。
- 模板含格式和公式；输出用独立读取方式检查，关键公式同时核对实际计算结果。
- 用户修改一个单元格后要求 AI 修改另一列，已有修改不能静默丢失。
- 文件改名、来源失效、任务切换、刷新、运行中断后恢复，不能混入其他任务的结果或宣称未知操作成功。
- 较大输入通过有界读取处理；超出支持范围时明确停止，不以截取前三张表或前若干字符冒充完整结果。

### 工程进入顺序

1. 先确认现有文件工具、导出链路及实际部署能力，画清原文件到交付文件的身份与授权路径。
2. 单独评审交付文件、版本、保存与保留策略的公共契约及兼容方案，补行为测试；工具输出与用户保存成果不能共享未经评审的自动过期语义。
3. 实现首版格式的文件访问、产出与检查，接入当前任务工作台。
4. 接通定向修改与版本冲突处理，覆盖流式展示、刷新和恢复。
5. 按仓库要求完成契约、组件快照、GUI 实际材料与相应运行时验证。

## 第二阶段：录制示范生成 Skill

用户流程：开始教学 → 操作并补充说明 → 查看整理后的步骤与变量 → 使用新材料试跑 → 修正 → 保存并使用。

第一版聚焦一个受支持浏览器中的取数、筛选、下载，再连接第一阶段的文件交付。桌面任意应用、复杂跨应用录制和无人值守外部写入不同时纳入首版。

录制保存任务相关的操作事件、可获得的页面元素信息和关键画面，供用户回看、删去无关步骤。密码和令牌不写入可分享 Skill，登录依赖执行时的独立授权。录制产物本身不授予后续操作权限。

生成的 Skill 草稿应包含：用途与触发描述、输入参数、所需应用与工具、步骤、完成标准、已知异常和需人工接管的位置。日期、文件名、筛选值按示范与用户说明提取为候选变量；不把示范中的固定值擅自泛化为永久业务规则。

SKILL.md 用来表达可移植的方法与约束；输入表单、录制证据、版本、授权与试跑记录由宿主管理。原始录制不整段注入每次执行的模型上下文，按需读取有界证据。优先调用现有可靠工具完成同一目标，界面操作需要时再使用。

一次示范只证明一条观察到的路径。单个用户 Skill 至少以一次新材料的真实试跑和实际结果核对支持确认激活，没有覆盖的分支明确记录；不同日期、不同输入文件和可处理异常的多样本覆盖属于产品发布验收，不要求每次教学都配置多套测试。用户接管后仅提出 Skill 修订建议，确认后形成新版本，保留旧版本可用范围。

验收重点：新材料下能完成交付、定位正确操作对象、能解释参数、异常时保留进度、不会重复已成功的写操作、用户能理解并修改生成的 Skill。

## 功能取舍

| 顺序       | 能力                                                 | 进入条件                                                         |
| ---------- | ---------------------------------------------------- | ---------------------------------------------------------------- |
| 先做       | 真实文件交付、检查、定向修改和版本                   | 首个跨行业流程贯通                                               |
| 随后       | 录制、参数整理、试跑、修正、保存 Skill               | 执行与交付链路可复用；Skill 保存加载边界已实现                   |
| 配套       | 从成功任务保存 Skill、引用成品模板、人工接管         | 复用同一技能身份与版本体系，解决观察到的教学摩擦                 |
| 接入与放大 | Skill 接入现有日程，按需支持批量输入                 | 补齐技能版本与参数绑定；单次执行、去重、累计预算和异常处理已验证 |
| 暂缓       | 行业首页、专门 CRM、独立承诺收件箱、复杂业务记忆图谱 | 真实重复使用证明通用界面已明显限制效率                           |

广度通过连接器和 Skill 扩展。为某个场景增加原生功能前，应确认其发生频率、实际人工成本、跨任务复用范围和验收方式；不能只凭竞品列表或演示效果排期。

## 用户验证与成败标准

以下是拟执行的验证方案与候选门槛，尚未招募、实施或得到结果。无需在用户材料未到位时等待，可以先使用合成材料完成工程行为验证；合成测试不能替代真实需求验证。

计划先招募 8–12 位每周有相似重复工作的用户，覆盖至少三个岗位；每人提供一次历史材料与合格成果，以及下一周期的新材料。访谈围绕上一次实际操作、返工、交付对象和花费时间展开，避免仅询问是否喜欢 AI。

分三次观察：人工基线；CrewON 首次交付（包括配置、教学、等待和返工）；换新材料再次执行。使用同等任务、交叉安排执行顺序；与 WorkBuddy 对照时记录版本、可用模型、工具和预算差异，不将单次随机结果归因于产品。

| 指标           | 口径与候选目标                                                                                   |
| -------------- | ------------------------------------------------------------------------------------------------ |
| 首次交付通过率 | 以任务开始前确定的业务标准评价；单独报告人工修改后通过率，不用用户点击完成代替正确性             |
| 人工投入       | 包含选材料、配置、示教、审批、检查和返工；重复执行的中位人工时间较人工基线降低至少 50%           |
| 教学回本       | 单独统计首次教学成本；候选目标为三个真实重复周期内累计节省时间覆盖教学与维护成本                 |
| 可靠性         | 列出的行为用例全部通过；关键合计错误、漏处理却宣称完整交付、覆盖用户修改和重复外部写入均阻止发布 |
| 重复使用       | 观察下一个实际工作周期是否主动再次使用，并记录放弃原因；不能把尚未到周期的人算作流失             |
| 成本与等待     | 记录每次尝试及最终合格成果的总模型/工具成本和端到端时间；未知费用保持未知                        |

如果主要时间仍花在检查修正，继续投入交付质量；如果每次复用都需要重新演示，优先修参数与执行稳定性；如果用户任务本身不重复，则减少示教优先级，保留一次性高质量交付。用户实际使用结果决定后续取舍。
