# 并行会话与执行耗时定位（2026-10-10）

本轮优先修复基础会话调度，业务插件保持卸载。页面、登录、工作空间、历史产物和模型选择器保持原样。

## 已确认的调度限制与修复

正式 Worker 入口原来只构造一个 `RuntimeWorker`。它的 `wake()` 在一次执行完成前返回同一个 drain Promise；正在等待模型流或工具返回时，不会领取另一个会话的工作项。这是跨会话排队的确定原因，不是两个会话真正同时执行。

生产入口现在默认两个独立执行通道，可通过 `CREWON_WORKER_CONCURRENCY` 配置 1–8 个。`CREWON_WORKER_ONCE=1` 仍只执行一次；组合库调用者默认仍为一个通道，原 `worker` 入口保留，新 `start()` 启动全部通道。配置在打开 Store 前验证，不修改数据库或 HTTP 协议。

每个通道仍有独立 Worker、租约、取消监听、资源作用域和 Store 生命周期；共享资源由组合根关闭一次，财务维护只供通道借用。退出时所有通道同步撤回执行权限，并在共享 transport 和 Store 释放前完成原清理。没有新增任务重试或恢复未知外部操作。

混合 Responses transport 原来的单条 WebSocket 不能交错执行两个模型流。现在仅当其他 Run 占用该 socket 时，当前 Run 使用同一配置和身份的既有 HTTP transport，并记录 `responses_websocket_busy`。这不关闭另一个 Run 的 socket，也不会永久降级以后请求；同一个 Run 的并发 WebSocket 调用仍按原规则拒绝。鉴权、内容校验、用量记录、重试预算及真实终止事件保持。

## 验证范围

真实 SQLite 和生产组合入口的四项本地集成测试通过：并发上限、两个 Run 的独立流式执行及第三个排队、取消一个不影响另一个、退出同时撤回并清理所有通道。慢会话保持未结束时，另一个会话能完成并腾出通道给第三个；各自只调用一次模型，结果和 attempt 不串线。正在流式执行时，新读连接能恢复各自提交的事件前缀，游标读取不重复；重新打开数据库保留完成结果。

Responses 全部 139 项测试通过，包括新增的真实本地 WebSocket/HTTP 并发测试，以及既有同 Run 流保护、恢复、取消、预算和计费校验。标准完整 Worker 回归共 2491 项：1955 通过、536 项既有环境条件跳过、0 失败。Worker 与 Responses 类型检查、仓库边界及文档格式检查通过。首次完整回归另有一项既有 candidate peer 返回 503；修正新增测试的事件身份字段后，按原命令重新完整运行通过，没有更改该 peer 测试或放宽检查。正式桌面更新尚待本轮验收；本地测试不能证明外部网关延迟已经消除。

## 仍未解决的外部延迟与失败

前一轮真实执行计时见 [模型响应耗时定位](./model-response-latency-20261009.md)：一个 Run 358.636 秒，其中本地工具累计约 3.86 秒，模型客户端链路约 345.76 秒；存在连接失败重试和 60 秒空闲超时。另一条流完整回复在 10.822 秒收齐，真实 terminal 在 32.106 秒才收到，额外等待约 21.284 秒。不能用网关网页展示的供应商时间代替客户端完整链路时间，也不能伪造终止事件来提早保存结果。

本轮只读正式数据库，最近失败包括 `responses_provider_invalid_prompt` 和 `responses_provider_server_is_overloaded`，不能归为并行冲突。保留的一条 `reconciling` 是历史未收尾状态，不代表当前仍有模型执行；没有删除、取消或重提它。对应供应商适配、网关状态和历史恢复仍需分别确认。

当前机器不带 API Key 的公开 `/v1/models` 探测，两次在 TCP 建连前超时（默认路径 20 秒；IPv4 直连 15 秒），均未收到 HTTP 响应，也未发起模型生成。这是当前链路不可达的证据，不能据此确定具体网络节点故障，也不能代替正式桌面的真实双会话及速度复测。

原正式数据库的两条历史 Run 与 7 / 3 条模型调用分段记录，已只读导出到 `output/plugin-foundation/parallel-20261010/historical-latency.json`。只导出固定身份、时间、状态和计时数字，不包含提示词、回答正文或凭据。
